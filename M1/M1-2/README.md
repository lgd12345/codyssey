# My Closet AI

사진으로 등록한 내 옷장과 개인 취향, 외출 날짜의 계절, 과거 코디 통계를 참고하는 AI 코디 웹 앱입니다. 배포 환경에서는 회원별로 개인 설정·옷장·대화를 Firestore에 보관합니다.

## 현재 상태

공개 환경에서 회원 로그인, Firestore 데이터 추가·조회와 요약 반영, AI 답변의 요약 건수 인용, 대화 저장 및 다시 불러오기를 확인했습니다. 기존 로컬 SQLite 자료는 `.local/`에 보존합니다.

- [프런트엔드 · Vercel](https://angle-closet.vercel.app/)
- [백엔드 API · Render](https://angle-closet-api.onrender.com/api/status)
- [Swagger UI](https://angle-closet-api.onrender.com/docs)

**현재 AI 연결:** Morrono의 New API 게이트웨이(`https://new-api.morrono.com/v1`), 모델 `gpt-6.1-terra`입니다. 게이트웨이의 모델 메타데이터와 공식 문서에서 OpenAI Chat Completions 호환 형식을 확인했습니다. OpenAI 본사 API 직접 연결을 뜻하지 않습니다.

**실제 사진 검증:** 일상복 셔츠 사진 1장을 실제 업로드 API로 요청해 반소매 셔츠·상의로 판별하고 저장·조회·다른 브라우저 접근 차단·삭제를 확인했습니다. 임시 로컬 DB에서 검증했으며 모킹하지 않았습니다. 결과는 `reports/morrono-vision-verification.json`입니다. 이 1회 결과를 모든 의류 사진의 정확성 검증으로 해석하지 않습니다.

로컬 `.env`는 `AI_PROVIDER=morrono`, `IMAGE_ANALYSIS_ENABLED=true`입니다. 키·모델·주소는 Git에서 제외된 `secrets/morrono-api.env`에서 읽습니다. 기존 제공자의 키를 새 서버에 재사용하지 않습니다. 자동 재시도·리디렉션을 끄고, 출력 상한은 사진 판별 512토큰·텍스트 추천 800토큰으로 제한합니다. 입력 이미지와 프롬프트도 사용량에 포함될 수 있습니다.

사진 기능을 끄려면 `IMAGE_ANALYSIS_ENABLED=false`로 설정하고 서버를 재시작합니다. 이 상태에서는 사진을 외부 AI에 보내거나 저장하지 않습니다.

시연용 데이터 기록 화면은 유지하며 한 페이지에 10건씩 표시합니다. 운영자 화면 분리는 추후 작업으로 보류합니다.

## 로컬 실행

검증 환경은 Python 3.12와 Windows입니다. 프로젝트 작업 디렉터리는 이 README가 있는 M1-2입니다. Git 저장소 루트는 두 단계 위이며 여기서 새 Git 저장소를 만들지 않습니다.

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install --index-url https://pypi.org/simple -r requirements.txt
```

`.env.example`을 참고해 `.env`를 설정합니다. 이미 `.env`가 있으면 덮어쓰지 마세요. 실제 키는 채팅·코드·README에 넣지 않습니다.

```dotenv
AI_PROVIDER=morrono
IMAGE_ANALYSIS_ENABLED=true
GARMENT_IMAGE_ENABLED=true
STORAGE_BACKEND=local
```

실행:

```powershell
.\.venv\Scripts\python.exe -m uvicorn backend.main:app --host 127.0.0.1 --port 8000 --no-access-log --limit-concurrency 16
```

또는 PowerShell에서 `./Start-Local.ps1`을 실행합니다. 보안 정책으로 스크립트 실행이 제한되어 있으면 정책을 낮추지 말고 위 Python 명령을 사용하세요.

- 화면: <http://127.0.0.1:8000>
- Swagger: <http://127.0.0.1:8000/docs>
- 종료: 실행한 터미널에서 Ctrl+C
- macOS/Linux에서는 `.venv/bin/python`을 사용합니다. 해당 환경의 실제 실행은 확인 안 됨입니다.

## 사용 흐름

1. 개인화 설정에서 스타일·더위/추위 민감도·옷장 테마·화면 밝기를 저장합니다. 옷장 테마(월넛/아이보리/세이지)와 밝은/어두운 모드는 독립된 설정입니다.
2. 옷장에 의류 사진을 등록합니다. 사진은 의류 검증을 위해 설정한 AI 제공자에게 전송됩니다. 손상·비의류·식별 불확실 사진은 최종 저장하지 않습니다.
3. 날짜와 외출 목적, 질문을 입력합니다. 추천 날짜는 한국 시간 기준 오늘부터 선택할 수 있습니다. 추천은 날짜의 계절에 맞는 의류를 우선하며, 외출 시간을 입력하면 함께 고려합니다. 과거 참고 데이터는 같은 계절에 게시된 코디의 구성 통계로 활용합니다.
4. 새 사진 등록 시 기본 아바타와 옷 원본으로 전신 착용 이미지 1장을 생성합니다. 윤곽을 요청할 때는 같은 이미지 모델에 착용 이미지만 보냅니다. 착용 결과와 윤곽을 확인한 뒤 필요하면 수정할 영역을 클릭해 더하거나 빼고, 기본 복장을 가릴 영역도 지정할 수 있습니다. 자동 윤곽을 끄고 직접 선택하는 것도 가능합니다. 검수한 윤곽은 아바타 좌표의 투명 레이어로 저장하며, 옷을 다시 입힐 때는 추가 생성 없이 합성합니다. 기본 민소매와 반바지는 옷장과 추천에 포함하지 않습니다.
5. 데이터 관리에서 기록을 추가·수정·삭제하면 요약과 그래프가 바뀝니다. 사용자 변경은 원본 JSON을 덮어쓰지 않는 개인별 변경 기록입니다.
6. 성공한 AI 대화는 자동 저장됩니다. 대화 기록에서 불러오기·이어가기·삭제가 가능합니다.

로그인 없는 개인화는 HttpOnly 쿠키의 임의 토큰과 서버의 해시 식별자로 구분합니다. 쿠키 삭제·다른 브라우저·다른 기기에서는 이전 자료를 복구하지 못할 수 있습니다. 수집 데이터의 원본 사용자 식별자는 앱 데이터에 포함하지 않습니다.

8008 로컬 시연 서버는 `CLOSET_LOGIN_REQUIRED=true`로 회원 로그인을 사용합니다. SQLite의 `users`, `garments`, `garment_images` 테이블을 회원 ID와 의류 ID로 연결하며, 비밀번호는 솔트와 해시로 저장합니다. 기존 Firestore 설정은 이 SQLite 회원 모드를 지원하지 않습니다. AI 제공자 키는 서버 환경 설정에서 읽습니다.

검수 중인 착용 이미지는 브라우저 세션별로 구분하며 서버 메모리에 최대 한 시간 동안 유지합니다. 검수한 레이어를 저장하면 옷장에 등록됩니다.
서버는 자동 윤곽을 착용 이미지와 같은 좌표로 변환합니다. 검수 화면에서 이미지를 확대하고, 영역의 가장자리를 클릭해 선택한 뒤 영역을 더하거나 뺄 수 있습니다. 선택 해제는 아직 반영하지 않은 점을 지우고, 되돌리기는 마지막 편집을 취소합니다. 자동 윤곽 요청과 착용 요청은 각각 한 차례이며, 윤곽 수정·저장·재착용에 추가 AI 요청은 없습니다.

## 구조와 책임

```text
backend/
  config.py       서버 환경 설정과 외부 AI 목적지 제한
  main.py         HTTP 경로, 출처/호스트/본문 크기/세션 검사
  schemas.py      Pydantic 요청·AI 응답 검증
  services.py     공통 통계, 계절별 참고 데이터, AI, 이미지 검증
  storage.py      소유 범위별 SQLite / Firestore 저장과 요청 한도
frontend/
  index.html      로그인 없는 개인화 화면
  styles.css      기본 화면·데이터·대화 스타일
  studio.css      반응형 드레스룸·독립된 테마와 화면 밝기
  assets/         반실사 기본 모델·빈 드레스룸 배경
  app.js          화면 상태·API 호출·대화 복원·그래프
data/             선별 데이터·출처 메타데이터·라이선스
scripts/          공식 원본에서 월별 균형 데이터 선별
```

라우터는 HTTP 입출력과 접근 검사, 서비스는 재사용할 집계·추천·사진 로직, 스키마는 자료형·범위·길이 검증, 저장소는 읽기·쓰기와 사용자 범위를 맡습니다. 모든 경로를 여러 파일로 먼저 나누는 불필요한 추상화는 만들지 않았습니다.

## 데이터와 통계

출처는 [ZOZO Research SHIFT15M](https://github.com/st-tech/zozo-shift15m)입니다. [공식 JSON](https://research.zozo.com/data_release/shift15m/label/iqon_outfits_with_tags.json) 2,555,147건을 스트리밍으로 끝까지 읽고 원본의 최근 12개 완전한 달에서 월별 83~84건, 계절별 250건씩 총 1,000건을 선별했습니다. 같은 날짜의 최대 허용량은 4건이며, 실제 선별 결과는 366개 날짜에 날짜별 2~3건입니다. 전체 원본은 프로젝트에 저장하지 않았습니다.

- 선별 기간: **2019-04-01 ~ 2020-03-31**
- `date`: 원본 `publish_date`인 게시일. 실제 착용일·촬영일이 아닙니다.
- `value`: 가방·액세서리를 포함한 코디 구성 아이템 수.
- `memo`: 원본 카테고리 ID와 태그에서 파생한 요약.
- `likes`: 원본 수집 시점 누적 좋아요 수. 일별 증가량이 아닙니다.
- 태그 누락은 빈 배열로 유지하며 허위 텍스트로 채우지 않습니다.
- 카테고리는 확인된 원본 ID를 그대로 표시하며, 확인되지 않은 이름을 붙이지 않았습니다.
- 계절은 게시월 기준(북반구)이며 실제 착용 계절이 아닙니다. 월별 균형 표본으로 자연 게시량·인기도·현재 유행을 주장하지 않습니다.
- 추가 통계는 카테고리별 등장 횟수, 그래프는 날짜별 평균 아이템 수입니다. CSV/JSON 다운로드와 테마 유지가 포함됩니다.

CC BY-NC 4.0: ZOZO Research에 출처를 표시하고 비상업적 조건을 준수해야 합니다. 라이선스 원문은 `data/SHIFT15M_LICENSE.txt`, 변경 내역·원본/선별본 SHA-256·선별 기준은 `data/shift15m_seasonal_1000.metadata.json`에 있습니다. 이전 최신순 표본은 비교용으로 보존하지만 앱에서는 읽지 않습니다. 원본 사진은 제공되지 않습니다.

선별 재현 명령 (기존 결과는 덮어쓰지 않습니다):

```powershell
.\.venv\Scripts\python.exe -m scripts.collect_seasonal_outfits
```

## API와 저장

| 메서드 | 경로 | 역할 |
|---|---|---|
| POST/GET | `/api/data` | 데이터 추가/페이지 조회 |
| PUT/DELETE | `/api/data/{id}` | 개인별 데이터 변경 |
| GET | `/api/data/summary` | 공통 요약 서비스 결과 |
| GET | `/api/data/export?format=csv` 또는 `json` | 안전한 내보내기 |
| POST | `/api/chat` | 검증된 AI 결과 반환 및 대화 자동 저장 |
| POST/GET | `/api/conversations` | 검증된 대화 생성·저장/목록 |
| GET/DELETE | `/api/conversations/{id}` | 대화 불러오기/삭제 |
| POST/GET | `/api/wardrobe` | 사진 검증 후 의류 등록/조회 |
| PUT/DELETE | `/api/wardrobe/{id}` | 의류 수정/삭제 |
| GET | `/api/wardrobe/{id}/image` | 소유 범위를 검사한 사진 응답 |
| GET/PUT | `/api/profile` | 개인 설정 조회/저장 |

`POST /api/conversations`는 임의 AI 답변 저장을 허용하지 않고 `/api/chat`와 같은 검증·생성·자동 저장을 사용합니다. 요청 스키마와 실제 예제는 Swagger에서 확인할 수 있습니다.

Firestore에서는 `data`, `conversations`, `wardrobe`, `profiles` 등의 최상위 컬렉션 안에 `{익명소유자해시}/records/{id}`로 저장합니다. `sessions`는 비밀 토큰 자체 대신 해시를, `usage`는 일별 AI 요청 한도를 저장합니다. 로컬 SQLite도 같은 논리적 범위를 사용합니다. 원본 1,000건은 읽기 전용 참조이며 `data`에는 사용자 추가/수정/삭제 기록을 저장하고 조회 시 합칩니다.

AI에는 전체 원본이 아닌 동일한 집계 함수의 요약, 현재 옷장 후보, 프로필, 조건, 최근 메시지 최대 12개를 전달합니다. 대화별 최대 100메시지·브라우저별 최대 100대화·옷장 100개로 제한합니다. 요청당 출력 상한은 1,600토큰, 동시 AI 호출은 프로세스당 2개, 기본 전역 일일 요청은 100회/브라우저당 30회입니다. 실패 요청도 예산에 포함됩니다. 일일 예산은 저장소에 유지되며 서버 재시작으로 초기화되지 않습니다.

요약은 모델이 모르는 사용자 데이터를 전달하고 화면과 답변 기준을 일치시킵니다. 원본의 세부 의미를 요약만으로 모두 설명할 수는 없습니다. 요약 기준 변경은 `services.summarize`에서 처리하고 화면·AI에서 함께 재사용합니다.

## Firestore 설정

Firebase 콘솔에서 Firestore와 서버 서비스 계정을 준비합니다. 서비스 계정 파일은 **이 프로젝트의 `secrets/` 안에만** 직접 저장하고 Git에 추가하지 마세요. 예:

```dotenv
STORAGE_BACKEND=firestore
FIREBASE_SERVICE_ACCOUNT_JSON=secrets/style-test-firebase-service-account.json
```

파일을 만든 뒤 서버를 재시작합니다. JSON 문자열을 서버 환경변수에 직접 설정하는 방식도 지원합니다. 브라우저는 Firebase 관리자 자격증명에 접근하지 않습니다. 초기화 실패 시 로컬 모드로 몰래 전환하지 않고 서버를 중지합니다. **현재 설정에서 실제 Firestore CRUD와 AI 대화 저장·조회 검증을 통과했습니다.**

## 보안과 배포 전 확인

Render의 Python Web Service는 Git 저장소의 `M1/M1-2`를 루트로 사용합니다. Vercel에는 같은 위치에서 버전 관리하는 프런트와 배포 설정만 추려 CLI로 배포했습니다.

- Render 빌드는 `pip install -r requirements.txt`, 시작은 `uvicorn backend.main:app --host 0.0.0.0 --port $PORT`, 상태 확인 경로는 `/health`입니다.
- Render에 `APP_ENV=production`, `STORAGE_BACKEND=firestore`, `CLOSET_LOGIN_REQUIRED=true`, Render 호스트의 `ALLOWED_HOSTS`, 실제 Vercel HTTPS 주소의 `ALLOWED_ORIGINS`를 설정합니다. Firebase 서비스 계정과 AI 키는 Render 서버에만 설정합니다.
- Firestore 시연 계정은 Firestore 환경을 설정한 뒤 프로젝트 루트에서 `python -m scripts.create_firestore_member`로 생성합니다. 로컬 SQLite 계정과 자료는 별도로 보관합니다.

- `.env`, `.local/`, `secrets/`, `.venv`는 Git에서 제외합니다. 프론트 정적 파일은 `frontend/`에서만 제공해 비밀 파일·DB를 내려받을 수 없도록 합니다.

- AI 반환 ID는 현재 소유 옷장에서 확인하고 외부 호출 이후에도 재검사합니다. HTML로 사용자 입력을 삽입하지 않으며 CSP·출처·Host·요청 빈도를 검사합니다.
- CSV 텍스트의 수식 시작 문자를 방어합니다. 비밀키·원본 이미지가 포함되지 않은 데이터만 내보냅니다.
- 로컬 서버는 `127.0.0.1`에만 바인딩합니다. 방화벽·백신·보안 정책을 낮추거나 라우터 포트를 개방할 필요가 없습니다.

- 운영에서는 HTTPS와 영속 Firestore를 사용하고 관리자 자격증명 최소 권한, 사용자/세션 보존·삭제 정책, 이미지 사용 비용, 제공자 자체 사용량 한도, 다중 인스턴스의 IP 제한, 백업·모니터링을 확인해야 합니다. 현재 로컬 검증만으로 공개 서비스의 보안을 보장하지 않습니다.

### 착용 이미지 후속 수정

- **같은 코디의 착용 방식별 전신 사진과 대표 사진 선택 (추후 작업).** 코디북이나 대화 기록에서 코디를 열고 “티셔츠를 바지 안에 넣어 입고 싶어요”처럼 착용 방식만 요청하면, 기존 의류 조합을 유지한 채 전신 착용 이미지 수정 요청으로 처리합니다. 현재는 착용 방식이 이미지 요청과 캐시 키에 전달되지 않아 같은 조합의 사진이 재사용됩니다. 이미지 요청을 준비할 때 착용 지시를 프롬프트와 캐시 키에 반영하고, 같은 조합과 같은 착용 지시의 사진만 재사용합니다. 새 착용 사진은 기존 사진과 함께 같은 코디에 별도로 저장하고, 사용자가 코디북에 표시할 대표 사진을 선택할 수 있게 합니다.
- **팔 안쪽 흰 테두리.** 흰 티셔츠 미리보기에서 팔과 몸통 사이의 투명한 틈에 티셔츠 옆선의 밝은 반투명 픽셀이 남았습니다. 노출 피부를 원본 픽셀로 복원한 뒤에도 남아 있어 피부 보정과 별개로 처리합니다. 실제 옷이나 팔 부분은 보존하고, 옷장 배경과 다크 모드 양쪽에서 가장자리를 확인합니다. 참고 이미지는 `reports/morrono-worn-skin-crop-preview.png`입니다.
- **셔츠 위에 재킷을 입힐 때 소매 노출.** 흰 셔츠와 베이지 재킷은 각각 단독 착용이 확인됐지만, 함께 입히면 셔츠 소매가 재킷 소매의 양옆으로 드러납니다. 확인 이미지는 `reports/wardrobe-registration-test/manual-shirt-and-jacket.jpg`입니다. 수정은 보류했습니다.
- **검은 넥타이 뒷면 라벨 노출.** 8006에서 자동 윤곽 추출은 성공했으나, 뒷면이 보이는 원본 사진의 라벨이 생성된 넥타이 앞면에 나타났습니다. 레이어는 저장하지 않았습니다. 추후 앞면 사진으로 매듭과 라벨 노출을 다시 확인합니다. 이번 원본은 `reports/wardrobe-registration-test/originals/07-black-tie.jpg`입니다.
- 전신 편집 결과를 사각형으로 자르고 원본 피부를 복원한 방식은 흰 티셔츠 1장으로 검증했습니다. 현재 `scripts/verify_garment_image.py`의 검증 경로에 있으며, 실제 옷장 등록·착용 경로에서 다른 의류와 함께 쓰는 것은 확인 안 됐습니다.

### 세 벌 로컬 등록·착용 검증

`scripts/wardrobe_crop_preview.py`는 로컬 8001번 포트의 격리 서버에서만 전신 편집과 사각형 자르기를 등록 화면에 연결합니다. 지정된 테스트 사진 세 장과 별도 SQLite 저장소를 사용합니다. 실제 테스트에서 흰 티셔츠, 면바지, 회색 맨투맨 순서로 사진 분석과 Sunburst 편집을 완료했고, 각각 저장하고 단독으로 입히는 데 성공했습니다. 새로고침 후 세 항목이 유지되고 맨투맨의 저장된 결과를 다시 입힐 수 있음을 확인했습니다.

**재현된 조합 오류.** 흰 티셔츠와 면바지를 함께 입히면 상의 사각형에 들어 있는 기본 흰 반바지와 피부가 면바지 상단을 덮습니다. 사진 분석이나 저장 오류가 아니라 사각형의 겹치는 영역을 교체하는 방식의 한계입니다. 확인 화면은 `reports/wardrobe-crop-02-combined.jpg`입니다.
