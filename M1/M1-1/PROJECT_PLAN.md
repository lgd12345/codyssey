> **진행 방식:** 파일별 전체 코드를 전달받아 복사·붙여넣기 → 실행 → 출력 검증

### 2.1 확인된 것과 미확인된 것

| 항목 | 현재 상태 | 개발 시 처리 |
|---|---|---|
| KAMIS에서 딸기 가격 자료 제공 | 공식 조회 사례 확인 | 실제 응답/다운로드 다시 확인 |
| 설향·상품·500g, 서울 등의 조건 선택 | 공식 조회 화면/설명에서 확인된 항목 | **동일 조합으로 전 기간 조회 가능한지는 미확인** |
| 후보 기간의 유효 관측일 100개 이상 | **미확인** | 실제 원본 자료로 **직접 계수** |
| 지역·품종·등급·단위·집계 방식이 일정함 | **미확인** | 수집된 열과 코드값 확인 후 고정 |
| 최종 원본 필드명·API 파라미터·파일 형식 | 실제 데이터 확인 전 | 응답 명세에 맞춰 수집 코드 확정 |
| 실제 추세·최저/최고·인사이트 | **분석 전** | 숫자를 가정하지 않고 실행 후 기록 |

**첫 번째 통과 조건(평가 1-1):** 한 가지 일관된 가격 조건(예: 동일 지역 또는 전국 평균, 동일 품종·등급·단위)으로 정제한 결과 **가격이 유효한 서로 다른 날짜 100개 이상**이 확보되어야 합니다. 동일 날짜에 여러 조건의 가격을 합산해 100개라고 계산하지 않습니다. 원본 행 수와 유효한 고유 날짜 수를 **서로 구분해** 기록합니다.

**100개 미만이라면:** (1) 수집 조건을 확인하고, (2) 동일한 조건으로 기간을 연장하며, (3) 필요한 경우 다른 집계 범위로 *전체 시계열을 일관되게* 다시 수집합니다. 기존과 다른 단위·등급·지역의 가격을 억지로 이어 붙이지 않습니다. 변경 사항은 `REPORT.md`에 기록합니다.

**검증:** 새 환경에서 의존성 설치 성공, API 키 등 비밀정보 미포함, `REQUIREMENTS.md`·계획서가 평가항목 1~4를 기준으로 일치하는지 확인

### STEP 02. KAMIS 원본 데이터 확보 (**최우선 위험 검증**)

**작업**
1. 공식 제공 경로에서 딸기 일별 소매가격 조회 가능 여부 확인
2. 후보 기간 2024-11-01~2025-05-31 조회
3. 품목·품종·등급·지역/집계 범위·가격 단위를 원본에서 확인
4. 원본을 `data/`에 보관하고 출처·수집일·조건 기록
5. 조건을 고정한 뒤 유효한 **고유 날짜 100개 이상인지 직접 검사**
6. 수집일, 공식 URL, 인증 필요 여부, 데이터 이용 조건, 수집 성공/실패 내역을 기록

**산출물:** `data/strawberry_raw.csv` 또는 재현 가능한 수집 스크립트, 출처·수집 조건·원본 규모 점검 기록  
**검증(평가 1-1, 1-7):** 원본 행 수 / 필터 적용 후 행 수 / 유효한 `date` 고유값 수 / 결측 가격 수 / 중복 행 수 / 시작·종료 날짜를 코드로 출력하고 `REPORT.md`와 `README.md`에 근거 기록

**이 단계가 통과하지 않으면:** 그래프·인사이트·게임을 만들지 않고 데이터 수집 조건을 먼저 재검토합니다.

### STEP 03. 데이터 정제

**작업**
1. 원본 열을 분석용 `date`, `price` 등으로 표준화
2. 날짜 변환, 오름차순 정렬, 단위·조건 통일
3. 결측·비수치·0원 이하 가격 검사
4. 같은 날짜에 여러 행이 있는 이유 확인 후 중복 기준 정하기
5. 급등락을 이상치 **후보**로 표시하고, 오류가 확인되지 않으면 삭제하지 않기
6. 관측이 없는 날짜와 가격이 결측인 날짜를 구분하고, 결측을 0원으로 채우지 않은 이유 기록
7. 급등락 확인 후보의 임시 기준(예: 직전 관측 대비 절댓값 20% 초과)을 실제 분포와 대조해 조정하고 **공식 이상치 기준으로 오인하지 않기**
8. 처리 전후 행 수·결측 수·유효 고유 날짜 수·제외 사유와 처리 기준을 **왜 선택했는지** 기록

**산출물:** `data/strawberry_clean.csv`, 결측·이상치 점검표, 전처리 전후 건수 및 선택 이유 기록  
**검증(평가 2-1, 2-2):** 원본 → 로딩 → 정제까지 각 단계의 입력·출력과 처리 기준을 설명 가능해야 하며, 정제 후 유효 날짜 100개 이상, 날짜 정렬, 가격 자료형·단위 일관성을 확인

### STEP 04. 시계열 분석 및 시각화

**분석 질문(최소 3개)**
1. 분석 기간 전체에서 가격이 어떻게 움직였는가?
2. 급등락한 시점과 변화 폭은 얼마인가?
3. 월별 평균 가격은 어떻게 다른가?

**기법(최소 2가지 결과 필수):** 최근 **7개 유효 관측일** 이동평균, 직전 유효 관측가격 대비 **가격 변화율**, 월별 평균 가격. 변화율은 `(현재 관측가 / 직전 유효 관측가 - 1) × 100`으로 계산하고, 관측일 사이의 공백을 확인합니다.

**기본 그래프 — 3개 전부 프로젝트 필수**
- `images/01_price_trend.png` — 일별 가격 추세(일별 변화·급변 구간)
- `images/02_moving_average.png` — 원가격과 7개 유효 관측일 이동평균 비교(단기 요동과 흐름 구분)
- `images/03_monthly_average.png` — 월별 평균 비교(월 단위 가격 수준 비교)

**그래프와 함께 반드시 설명할 내용**
1. 분석 질문 **3개 이상**에 그래프나 계산 결과가 실제로 대응하는지 확인합니다.
2. 이동평균은 **왜 추세를 보기 위한 것인지**, 변화율은 **왜 급등락 확인에 쓰는지**를 실제 날짜·수치로 설명합니다.
3. 일별·월별·**7개 관측일**이라는 집계 단위와 선택 이유를 기록합니다. 7개 관측일은 7달력일이 아닙니다.
4. **트렌드/계절성/노이즈 중 최소 1개**를 그래프의 구간·수치에 연결해 설명합니다. 한 시즌의 월별 차이만으로 반복적인 계절성을 확정하지 않습니다.
5. `REPORT.md`에 이동평균·변화율 **두 기법의 결과값**을 최소 1개 이상의 대표 날짜/구간과 함께 실어야 합니다. 코드 내부에서 계산만 하고 보고서에서 빠뜨리면 미통과입니다.

**산출물:** 재실행 가능한 `analysis.py` 또는 `analysis.ipynb`, **기본 그래프 3개**, 이동평균·변화율 결과표/대표 수치 및 집계 단위 설명  
**검증(평가 1-2~1-5, 2-3, 3-1, 3-2):** 세 그래프의 이미지 링크, 축·단위·날짜 정렬, 빈 날짜 구간과 축 스케일, 원본 가격과 대표 이동평균·변화율의 계산값을 대조

### STEP 05. 선택한 보너스: 간단 예측

**작업**
1. 날짜 순서로 학습/검증 구간 분할(예: 끝부분 20개 관측값 검증)
2. 다음 관측일 가격을 직전 관측일 가격으로 예측하는 **나이브 방식** 적용
3. 검증 구간 실제값과 비교하고 MAE 계산
4. `images/04_baseline_prediction.png` 저장
5. 데이터 누수 여부와 예측 가정·한계 설명
6. 보너스 결과를 `REPORT.md`에 **평가 오차, 그래프, 가정·한계**와 함께 별도 섹션으로 작성

**산출물:** 예측 코드, 예측 그래프, 검증 오차, 한계 설명  
**검증:** 미래 실제값을 예측 시점에 미리 참조하지 않았는지 확인; 마지막 관측가격을 쓰는 **1-step 예측**과 검증 구간의 실제 가격을 비교했는지 점검. 예측 그래프는 기본 시각화 3개에 **별도로 추가**

### STEP 06. 인사이트 및 `REPORT.md` 작성

**필수 목차(최신 `REQUIREMENTS.md` 8절과 동일)**
1. 분석 주제 및 선정 이유
2. **분석 질문 3개 이상**

## 7. 복사·붙여넣기 방식의 진행 규칙

1. **한 단계씩:** 다음 단계의 코드를 먼저 추가하지 않고 이전 단계 실행 성공을 확인합니다.
2. **파일별 전체 코드 제공:** 파일명·저장 위치·코드 전체를 함께 제공합니다.
3. **명령어도 복사 가능하게:** 설치/실행 명령을 그대로 실행할 수 있는 형태로 작성합니다.
4. **검증 기준 제시:** 실행 후 생성되어야 하는 CSV·PNG와 확인해야 하는 숫자를 함께 안내합니다.
5. **실제 데이터 우선:** CSV가 확보되기 전에는 그래프 수치, 인사이트, 예측 성능을 만들어 넣지 않습니다.

7. **독립 검증:** AI가 만든 계산은 대표 날짜 2~3개를 원자료 및 독립 계산과 대조하며, 해석은 사실·가설로 구분합니다.
8. **오류 수정은 해당 단계에서:** 오류가 발생하면 해결하고 통과한 후 다음 단계로 진행합니다.
9. **비밀정보 보호:** API 키를 소스와 문서에 그대로 적거나 GitHub에 올리지 않습니다.
