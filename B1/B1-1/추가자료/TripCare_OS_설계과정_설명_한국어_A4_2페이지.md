# TripCare OS 설계 과정 문서

이 문서는 TripCare OS를 설계하면서 어떤 문제를 발견했고, 이를 해결하기 위해 어떤 구조로 발전시켰는지를 쉽게 이해할 수 있도록 정리한 설계 기록이다. 단순히 최종 결과를 설명하는 것이 아니라 설계가 어떤 이유로 변경되었는지와 각 설계 결정의 배경을 함께 담았다.

## 1. 설계를 시작한 이유

기존의 일반적인 여행 GPT는 질문이 들어올 때마다 독립적으로 답변하는 경우가 많다. 이 방식은 대화가 길어질수록 이전 결정과 충돌하거나 이미 정한 내용을 다시 제안하는 문제가 발생한다. 예를 들어 호텔을 이미 선택했는데 다른 호텔을 다시 추천하거나, 날짜를 변경했는데도 이전 교통편을 그대로 사용하는 문제가 생길 수 있다. TripCare OS는 이러한 문제를 해결하기 위해 여행을 하나의 프로젝트처럼 관리하는 것을 목표로 설계되었다.

## 2. 설계가 발전한 과정

초기 버전은 필요한 기능을 나열하는 방식이었다. 하지만 기능이 많아질수록 규칙이 중복되고 실행 순서가 불분명해졌다. 그래서 설계를 Kernel(항상 지켜야 하는 원칙), Runtime(실행 절차), State(여행 상태), Module(세부 기능) 구조로 재편하였다. 이 구조는 새로운 기능을 추가해도 기존 구조를 크게 수정하지 않아도 되는 장점이 있다.

## 3. Runtime을 만든 이유

모델이 같은 질문에도 다른 순서로 사고하면 결과가 달라질 수 있다. 이를 줄이기 위해 모든 요청을 '의도 파악 → 상태 불러오기 → 상태 갱신 → 제약 검증 → 최신 정보 확인 → 후보 생성 → 평가 → 추천 → 최종 점검' 순서로 처리하도록 정의하였다. 이렇게 하면 응답의 일관성이 높아지고 불필요한 재계산도 줄일 수 있다.

## 4. State 관리

TripCare OS의 핵심은 상태(State)이다. 여행지, 날짜, 예산, 교통, 숙소, 일정, 확정된 예약, 보류된 선택 등을 각각 관리한다. 사용자가 일부만 수정하면 영향을 받는 부분만 다시 계산하고 나머지는 그대로 유지한다. 이 덕분에 긴 여행 계획에서도 처음부터 다시 계획을 세울 필요가 없다.

## 5. 현실성 중심 설계

이번 설계에서 가장 중요하게 추가된 정책은 현실성(Candor) 정책이다. 기술적으로 가능하다는 이유만으로 좋은 계획이라고 판단하지 않는다. 예를 들어 하루에 너무 많은 도시를 이동하거나 환승 시간이 지나치게 짧은 일정은 '가능'이 아니라 'Fragile' 또는 'Unrealistic'으로 분류한다. 사용자를 기분 좋게 만드는 답변보다 실제 여행에서 성공할 가능성이 높은 답변을 우선하도록 설계하였다.

## 6. Hardening Layer

규칙만으로는 모델이 상황에 따라 다르게 행동할 수 있기 때문에 마지막에 Hardening Layer를 추가하였다. 여기에는 규칙 우선순위, Fail-Closed 정책, Feasibility Gate, Recommendation Threshold 등이 포함된다. 즉, 중요한 정보가 없으면 무리하게 추천하지 않고, 실행 가능한 경우에만 추천하도록 제어한다.

## 7. Few-shot 예시를 추가한 이유

긴 규칙보다 짧은 행동 예시가 모델의 실행 방식에 더 큰 영향을 주는 경우가 있다. 그래서 문서 마지막에 '비현실적인 일정'과 '예산 부족' 사례를 간단한 예시로 추가하였다. 이를 통해 규칙을 실제 응답으로 연결하도록 유도하였다.

## 8. 최종 목표

최종적으로 TripCare OS는 단순한 여행 추천 챗봇이 아니라 여행 계획의 상태를 지속적으로 관리하고, 변경 사항의 영향을 분석하며, 현실적으로 실행 가능한 선택지만 제안하는 여행 의사결정 운영체제를 목표로 한다. 앞으로는 장기 사용자 선호 학습, 외부 서비스 연동, 자동 상태 저장 등의 기능을 추가하여 완성도를 높일 계획이다.
