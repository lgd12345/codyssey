# TripCare 시스템 설계 문서

## 0. 한눈에 보는 설계

| 항목     | 내용                                                  |
| ------ | --------------------------------------------------- |
| 업무 과업  | **사용자 조건에 맞는 실행 가능한 여행지 추천**                        |
| 타겟 사용자 | 검색·가격 비교가 어렵고 예산·이동 부담을 함께 고려해야 하는 여행자              |
| 핵심 입력  | 출발지, 날짜/기간, 예산 범위, 동행자, 여행 목적, 선호·회피 조건             |
| 핵심 출력  | 후보 비교, 최종 추천 또는 추천 보류, 근거, 위험·확인 필요 사항, 다음 행동       |
| 핵심 원리  | 상태 유지 → 필수 조건 확인 → 최신 정보 검증 → 실행 가능성 판정 → 요청 범위만 출력 |
| 최종 구성  | TripCare OS Production v1.4                         |

## 1. 문제 정의와 사용자

일반 여행 챗봇은 취향만 반영하고 가격, 이동 시간, 보행량, 운영 여부를 충분히 검증하지 않은 채 “가능하다”고 답할 수 있다.

&#x20;TripCare는 다음 문제를 해결한다.

* 사용자가 원하지 않는 일정과 예산표까지 길게 생성하는 문제

* 빠듯한 예산을 근거 없이 가능하다고 판단하는 문제

* 폐업·변경 가능성이 있는 장소나 가격·운항편을 확정적으로 말하는 문제

* 이미 제공한 조건을 다시 묻거나, 조건 변경 후 이전 결론을 유지하는 문제

**타겟 사용자**는 여행 경험이나 검색 시간이 부족하고, 예산·체력·환승 부담을 함께 고려해야 하는 사용자이다.

## 2. 입력과 출력 규격

### 2.1&#x20;

### &#x20;v1 입력 템플릿과 비교용 동일 입력

​

현재 **TripCare OS Production v1.4에는 별도의 고정 입력 템플릿이 존재하지 않는다.​**&#x20;

사용자는 자연어로 자유롭게 요청하며, 시스템은 대화에서 이미 제공된 조건을 추출하고 결과에 중대한 영향을 주는 누락 정보만 질문한다.

아래 양식은 Production 버전의 입력 템플릿이 아닌

&#x20;**v1 프롬프트에서 실제로 사용했던 원문 입력 형식**이다.

#### v1 프롬프트 원문

```
아래 정보를 바탕으로 맞춤형 여행지를 추천하고 여행 준비 체크리스트를 작성하세요.
[여행 목적] :
[여행 기간] :
[희망 여행 지역] :
[예산] :
[동행자] :
[선호 여행 스타일] :
[계절] :
[추가 요청사항] :
```

​

#### v1과 v2 비교에 사용한 동일 입력

```
[여행 목적] : 쇼핑
[여행 기간] : 3박 4일
[희망 여행 지역] : 일본
[예산] : 60만 원
[동행자] : 친구
[선호 여행 스타일] : 쇼핑을 하면서 카페에 가서 맛있는 음료나 디저트를 먹고 예쁜 풍경을 보는 것을 좋아한다.
[계절] : 겨울
[추가 요청사항] : 너무 오래 걷는 것을 안 좋아하고 동선이 복잡한 건 싫다.
```

이 동일 입력을 v1과 후속 프롬프트 구성에 적용해 모호성 처리, 현실성 판정, 상태 일관성, 환각 억제, 출력 범위 제어를 비교했다.

### 2.2 출력 규격

1. **조건 요약**: 새로 확인되거나 변경된 핵심 조건만 표시한다.

2. **실행 가능성**: Practical / Demanding / Fragile / Unrealistic / Infeasible / Indeterminate 중 하나로 내부 판정한다.

3. **후보 비교**: 추천 요청 시에만 유효 후보 3개 이내를 비교한다.

4. **결론**: 최종 추천, 추천 보류 또는 조건 충돌을 명확히 말한다.

5. **근거와 불확실성**: 검증 정보와 추정 정보를 구분한다.

6. **다음 행동**: 예약 전 확인 등 필요한 행동 1\~3개만 제시한다.

예산·날짜처럼 실행 가능성을 좌우하는 정보가 없으면 최대 3개만 되묻는다. 사용자가 단순히 조건을 추가하거나 수정한 경우에는 새 추천이나 예산표를 임의 생성하지 않는다.

​

## 3. 프롬프트 구조

### 3.1 시스템 프롬프트

시스템 프롬프트는 다음 규칙을 담당한다.

* 대화 전체를 하나의 여행 상태로 관리

* Mandatory / Preferred / Unknown 조건 분류

* 사실, 추론, 미확인 정보 구분

* 가격·운항·운영시간·정책 등 변동 정보 재검증

* 필수 조건을 만족한 후보만 추천

* 조건 변경 시 영향받는 결론만 무효화

* 추천·선택·예약·확정을 서로 다른 상태로 관리

* 요청하지 않은 일정·예산·체크리스트 출력 금지

전체 시스템 프롬프트는 별도 첨부물 `TripCare_OS_CustomGPT_Production_EN_v1.4.md`로 관리한다.

### 3.2 사용자 프롬프트

사용자 프롬프트는 자유 형식 또는 2.1의 템플릿을 사용한다. 챗봇은 이미 제공된 항목을 추출하고, 결과에 중대한 영향을 주는 누락 정보만 질문한다.

### 3.3 입력 템플릿

입력 템플릿은 사용자가 반복 복사할 수 있는 데이터 수집 양식이다. 시스템 규칙이나 역할 지시와 분리해 재사용성을 높였다.

​

## 4. 동작 절차

```text
1. 현재 요청의 유형 분류
2. 기존 여행 상태 불러오기
3. 새 조건 추가·수정 및 종속 결론 무효화
4. 사용자가 요청한 산출물 범위 확정
5. 필수 조건과 결정적 미확인 정보 점검
6. 변동 정보가 중요하면 최신 근거 확인
7. 실행 가능한 후보만 비교·추천
8. 사실성·상태 일관성·출력 범위 최종 감사
```

핵심 설계는 \*\*검증 전 추천 금지(Feasibility Gate)\*\*이다. 경로, 시간, 필수비용, 안전·법적 조건, 접근성, 운영 여유가 확인되지 않으면 긍정 추천 대신 “판정 불가” 또는 “추천 보류”를 출력한다.

​

## 5. v1 → v2 → Production 개선

| 구분    | v1 기본 프롬프트     | v2 설계안      | Production v1.4            |
| ----- | -------------- | ----------- | -------------------------- |
| 상태 관리 | 없음             | 문맥 유지 규칙 추가 | 변경 영향만 재계산, 여행별 상태 분리      |
| 확인 질문 | 기준 없음          | 최대 3개       | 결과를 바꾸는 질문만 수행             |
| 예산 판단 | 임의 추정 가능       | 포함 범위 확인    | 필수비용·변동성·편안함까지 검토          |
| 최신성   | 규칙 없음          | 확인 필요 표시    | 변동 정보는 재검증, 근거 수준 구분       |
| 출력 제어 | 일정·체크리스트 과다 출력 | 요청 범위 제한    | 정보 추가만 한 경우 산출물 생성 금지      |
| 실패 처리 | 가능한 방향으로 답변    | 어려움과 대안 제시  | 유효 후보가 없으면 충돌과 최소 완화 조건 제시 |

**개선 이유:​** 실제 대화에서 60만 원 전체 예산에 대해 실시간 가격을 충분히 검증하기 전에 후쿠오카 예산 배분과 일정을 생성했고, 장기 대화에서는 “9월 둘째 주”가 “셋째 주”로 바뀌는 상태 오류가 나타났다. Production 버전은 이 두 실패를 직접 방지하도록 설계했다.

​

### 5.1 실제 채팅을 반영한 수정 과정 요약

두 개의 채팅 기록과 별도 설계과정 문서를 바탕으로, 프롬프트를 단순히 길게 확장하는 대신 **실제 실패를 일반 규칙으로 바꾸는 방식**으로 수정했다.

| 확인된 문제                                | 수정한 설계                                                                 |
| ------------------------------------- | ---------------------------------------------------------------------- |
| 여행 목적이 확인되기 전에 후쿠오카를 먼저 추천함           | 추천 결과를 크게 바꾸는 목적·예산·인원부터 확인하도록 질문 우선순위를 설정                             |
| 60만 원 전체 예산을 검증하지 않고 일정과 항목별 예산을 생성함  | Feasibility Gate와 출력 범위 제어를 추가해, 검증 전 가능 판정과 요청하지 않은 일정 생성을 금지         |
| 대화가 길어지며 날짜·숙소·식당 등 확정 조건이 바뀌거나 누락됨   | 자연어 대화 전체가 아니라 구조화된 TripState로 확정·제안·폐기 상태를 분리하고, 변경 영향만 재계산           |
| 기능과 예외 규칙이 계속 추가되어 실행 순서가 불명확해짐       | 프롬프트를 Kernel–Runtime–State–Module 구조로 재편하고, 모든 요청을 동일한 Runtime 순서로 처리  |
| 특정 사례마다 별도 규칙을 추가해 프롬프트가 편협해질 위험이 생김  | 렌터카 등 개별 상황 전용 규칙보다 제약 확인, 현실성 판정, 상태 갱신 같은 범용 규칙을 우선                  |
| 자체 작성한 모범 답변을 실제 모델 검증 결과처럼 볼 위험이 있었음 | 정적 규칙 검토·역할 시뮬레이션과 독립 모델 실행 검증을 구분하고, 실제 실행하지 않은 수치는 벤치마크로 주장하지 않도록 수정 |

설계 변경은 `실패 사례 확인 → 원인 분류 → 최소 규칙 수정 → 기존 통과 사례 재점검` 순서로 진행했다. 최종 버전에는 상태 관리, 현실성 중심 판단, Fail-Closed 정책, 추천 문턱, 근거 수준 구분, Few-shot 행동 예시를 남겼다. 반면 특정 교통수단이나 여행 유형 하나에만 적용되는 과도한 전용 규칙은 줄여 다른 여행 상황에도 적용할 수 있도록 했다.

## 6. 3종 모델/구성 비교

동일한 여행 입력을 세 가지 프롬프트 구성에 적용한 결과를 5점 척도로 평가했다. 기반 LLM이 완전히 다른 3개 상용 모델의 벤치마크가 아니라, **동일 업무에서의 세 가지 프롬프트 모델(구성) 비교**이다. 따라서 결과는 프롬프트 개선 효과를 평가하는 용도로 한정한다.

평가 입력: 부산 출발, 일본 3박 4일, 1인 총예산 60만 원, 쇼핑·카페·풍경 선호, 장시간 보행·복잡한 환승 회피.

| 평가 축       | v1 기본 | v2 설계안 | Production v1.4 | 근거                                         |
| ---------- | ----: | -----: | --------------: | ------------------------------------------ |
| 모호성 처리     |     1 |      4 |               5 | v1은 즉시 추천, 이후 버전은 예산 기준·포함 범위를 확인          |
| 현실성 판정     |     2 |      3 |               4 | v2도 검증 전 “가능” 표현이 있었고 Production은 추천 문턱 강화 |
| 상태 일관성     |     1 |      3 |               4 | 실제 장기 대화의 날짜 혼동을 상태 전이 규칙으로 보완             |
| 환각 억제      |     2 |      3 |               4 | 최신 확인 표시에서 근거 등급·추천 보류 방식으로 강화             |
| 출력 범위 제어   |     1 |      4 |               5 | v1은 일정·예산표를 과다 생성, Production은 명시 요청 필요    |
| **총점 /25** | **7** | **17** |          **22** | 업무상 비용 손실과 헛수고 방지에 가장 적합                   |

**선정:​** Production v1.4. 여행 추천은 창의성보다 가격·운영·상태의 정확성과 실패 시 보수적 판단이 중요하기 때문이다.

​

## 7. Few-shot 행동 예시

### 예시 1 — 이론적으로 가능하지만 비현실적인 경우

**사용자:​** “하루에 멀리 떨어진 도시 세 곳을 방문하고 밤 9시 전에 호텔로 돌아오고 싶어.”

**올바른 행동:​**

> 이 일정은 이상적인 조건에서만 이론적으로 가능하지만 실용적인 일정은 아닙니다. 대부분의 시간이 이동에 쓰이고 한 번의 지연으로 전체 일정이 깨질 수 있습니다. 도시 한 곳으로 줄이거나 이틀로 늘리는 것이 필요합니다.

**잘못된 행동:​**

> 바쁘겠지만 아마 가능할 거예요.

### 예시 2 — 제시된 예산으로 편안하고 현실적인 여행이 어려운 경우

**사용자:​** “모든 여행경비를 포함해 60만 원으로 일본 3박 4일 여행이 가능해?”

**올바른 행동:​**

> 현재 조건만으로는 편안하고 현실적인 여행이 가능하다고 판단하기 어렵습니다. 필수비용, 가격 변동성, 예상하지 못한 지출 위험을 고려하면 예산이 지나치게 빠듯할 수 있습니다. 비상 여유금을 두지 않더라도 예산 초과 위험이 높을 수 있으므로, 이 예산에 억지로 여행을 맞추는 것은 권하기 어렵습니다. 정확한 출발 날짜와 출발지, 여행 인원, 그리고 60만 원이 1인 기준인지 전체 예산인지 알려주세요.

**사용자:​** “비상 여유금은 필요 없어.”

**올바른 후속 행동:​**

> 비상 여유금을 두지 않는다고 해서 여행이 자동으로 가능해지는 것은 아닙니다. 오히려 예상하지 못한 지출을 감당할 여지가 사라집니다. 필수비용과 현실적인 가격 범위를 확인한 뒤에도 예산이 지나치게 빠듯하다면, 일정이나 예산을 억지로 맞추지 않고 어렵다고 안내해야 합니다. 정확한 출발 날짜와 출발지는 어디인가요?

**잘못된 행동:​**

> 비상 여유금이 필요 없다면 가능합니다.

> 그러면 60만 원 전액을 항공권과 숙박비에 배분하겠습니다.

> 그 예산에 맞춰 후쿠오카 3박 4일 일정을 작성하겠습니다.

사용자가 비상 여유금을 두지 않겠다고 답하더라도 이를 여행이 가능하다는 근거로 사용하지 않는다. 필수비용, 가격 변동성, 예상하지 못한 지출 위험, 사용자가 원하는 여행의 편안함을 보수적으로 평가한다. 여전히 편안하고 현실적인 여행이 어렵거나 예산 초과 위험이 높다면 그 사실을 직접 알리고, 일정이나 항목별 예산을 억지로 맞추지 않는다. 예산의 범위를 알게 되더라도 사용자가 명시적으로 요청하지 않은 일정, 예산안, 비용 추정, 항목별 가격, 비용 배분 또는 추천을 생성하지 않는다.

### 예시 3 — 이미 제공된 정보를 다시 묻거나 성급하게 계획을 확정하는 경우

**사용자:​** “부산에서 출발해 친구와 겨울에 일본으로 3박 4일 여행을 가고 싶어. 예산은 60만 원이고, 쇼핑과 카페, 디저트, 예쁜 풍경을 좋아해. 오래 걷거나 복잡하게 이동하는 일정은 싫어.”

**올바른 행동:​**

> 현재 조건에서는 주요 쇼핑·카페 지역이 비교적 밀집되어 있고 복잡한 이동을 줄이기 쉬운 후쿠오카가 우선 검토 대상입니다. 다만 예산의 범위가 명확하지 않아 아직 여행의 실행 가능성을 판단할 수 없습니다. 60만 원은 항공권과 숙박을 포함한 1인 기준의 전체 여행 예산인가요?

**잘못된 행동:​**

> 후쿠오카가 가장 적합합니다. 1일 차에는 하카타, 2일 차에는 텐진, 3일 차에는 모모치를 방문하세요. 예상 항공료와 숙박비를 합하면 충분히 가능합니다. 겨울 중 몇 월에 출발하시나요?

이미 제공된 정보를 다시 묻지 말고, 핵심 미확정 조건이 해결되기 전에는 장문의 일정, 검증되지 않은 비용 추정, 또는 확정적 추천을 먼저 제시하지 않는다.

### 예시 4 — 여행 목적을 확인하기 전에 성급하게 추천하는 경우

**사용자:​** “부산에서 출발해서 3박 4일 정도 일본에 가고 싶어.”

**올바른 행동:​**

> 부산 출발 3박 4일이면 일본의 여러 지역을 후보로 볼 수 있습니다. 다만 가장 적합한 목적지는 이번 여행에서 원하는 경험에 따라 크게 달라집니다. 휴양과 휴식, 온천, 먹거리, 쇼핑, 자연, 도심 관광 중에서 가장 중요하게 생각하는 것은 무엇인가요?

**잘못된 행동:​**

> 부산 출발이라면 후쿠오카가 가장 현실적인 선택입니다. 후쿠오카, 오사카, 도쿄도 있습니다. 여행 날짜와 예산, 동행 인원을 알려주세요.

추천 결과를 가장 크게 바꾸는 미확정 정보를 확인하기 전에 특정 목적지를 최적의 선택으로 단정하지 않는다.

## 8. 환각 정의와 검증 결과

### 8.1 정의

이 과제에서 환각은 **검증 가능한 사실·수치·가격·운항편·운영시간·정책을 근거 없이 사실처럼 생성하는 오류**이다. “감성적인 코스 이름 만들기” 같은 창의적 생성은 사실 주장으로 오인시키지 않는 한 환각으로 보지 않는다. 여행 과업에서는 사실 오류가 예약 실패, 추가 비용, 헛걸음으로 이어지므로 창의성과 분리해 평가한다.

### 8.2 판정 기준

* **Pass A:​** 정확한 사실과 확인 가능한 근거를 제시함.

* **Pass B:​** 확인할 수 없거나 변동 가능함을 명시하고 공식 확인 경로·필요 조건을 제시함.

* **Fail:​** 미확인 정보를 단정하거나, 근거 없는 수치·장소·가능 여부를 생성함.

### 9.1 유지에 성공한 상태

장기 대화 중에도 다음 조건은 비교적 안정적으로 유지되었다.

* **여행 인원 5명:​** 50대 부부 2명, 20대 1명, 조부모 2명으로 확정된 뒤 이후 숙소·식사·차량 일정에서 5명 기준을 계속 사용했다.

* **조부모 2명 고려:​** 숙소 주차 편의, 짧은 이동 거리, 휴식 시간, 무리하지 않는 해변 산책 등 고령 동행자의 체력 부담을 일정 판단에 반영했다.

* **동선 중시:​** 자가용 이동, 주차 가능 여부, 관광지 간 이동시간, 숙소 체크인 후 휴식 등을 고려해 이동 횟수를 줄이려 했다.

* **알레르기 유지:​** 조개류·갑각류 알레르기를 이후 식당 추천에서도 삭제하지 않았고, 해산물 전문점 대신 한우·돼지고기 중심 식사를 제안했다.

* **숙소 조건 유지:​** 더블침대 2개, 조식, 주차, 5명 수용 여부와 예산 변경을 계속 비교했다.

이 부분은 장기 문맥에서 모든 정보를 잃은 것이 아니라, **핵심 인원·건강·이동 제약은 상당 부분 유지했다는 성공 사례**로 평가할 수 있다.

### 9.2 날짜 상태 드리프트 실패

사용자가 확정한 날짜는 **9월 둘째 주 토요일**이었지만, 이후 일정 정리에서 챗봇이 이를 **9월 셋째 주 토요일**로 변경했다. 사용자가 “셋째 주라고 했지 않아?”라고 유도했을 때도 기존 확정 상태를 조회하지 않고 셋째 주가 맞다고 동의했으며, 마지막에 사용자가 다시 “둘째 주였어”라고 지적한 뒤에야 수정했다.

이는 단순 표현 실수가 아니라 다음과 같은 상태 관리 실패이다.

* 확정된 `date` 필드보다 직전 사용자 표현을 우선함

* 사용자의 확인 질문을 새로운 사실로 잘못 덮어씀

* 일정 전체를 재작성하면서 잘못된 날짜를 반복 확산함

* 최종 출력 전 `confirmed date` 대조를 수행하지 않음

따라서 날짜 오류 사례는 삭제하지 않고, 장기 문맥 유지의 대표적인 **Fail 사례**로 보존한다.

### 9.3 요청한 흑돼지 식당 누락 실패

사용자는 저녁 식사로 특정 흑돼지 고깃집을 일정에 넣어 달라고 요청했지만, 챗봇은 해당 식당명을 정확히 유지하지 않고 일반적인 “흑돼지 전문점”으로 바꾸거나 다른 식당 정보를 일정에 포함했다. 즉, 사용자의 선택을 `Selected restaurant`로 저장하지 않고 단순한 음식 카테고리로 축약했다.

이 실패의 핵심은 다음과 같다.

* 사용자가 지정한 특정 식당을 확정 상태로 저장하지 않음

* “흑돼지”라는 업종만 유지하고 식당명은 누락함

* 이후 일정 생성 시 다른 식당이나 일반 표현으로 대체함

* 사용자가 요청하지 않은 대체안을 확정 일정처럼 제시함

이 사례는 알레르기와 음식 종류는 기억했지만, **사용자가 선택한 구체적 장소를 보존하지 못한 부분적 문맥 실패**이다. 향후에는 식당을 다음처럼 별도 상태로 관리해야 한다.

```text
restaurant_state = {
  selected_name: "사용자가 지정한 흑돼지 식당",
  cuisine: "흑돼지",
  allergy_constraints: ["shellfish", "crustaceans"],
  verification_status: "unverified",
  substitution_allowed: false
}
```

### 9.4 구조화 상태 개선안

```text
TripState = {
  confirmed: {
    travelers: 5,
    traveler_profile: ["50대 2명", "20대 1명", "조부모 2명"],
    date: "9월 둘째 주 토요일",
    transport: "자가용"
  },
  mandatory: {
    mobility: "짧은 동선·적은 보행·주차 편의",
    allergies: ["조개류", "갑각류"],
    beds: "더블침대 2개",
    breakfast: true,
    budget_cap: "latest confirmed value"
  },
  selected: {
    accommodation: "소노캄 거제",
    dinner: "사용자가 지정한 흑돼지 식당"
  },
  proposed: {
    attractions: ["거제조선해양문화관", "와현해수욕장"],
    cafe: "On The Sunset"
  },
  stale: {
    date_dependent_price: true,
    availability: true,
    restaurant_operation: true
  }
}
```

조건 수정 시 해당 필드와 종속 항목만 갱신해야 한다. 답변 전에는 최소한 다음 네 가지를 자동 대조한다.

1. 출력 인원과 `confirmed.travelers`가 같은가.

2. 일정이 조부모의 이동 부담과 알레르기 조건을 위반하지 않는가.

3. 출력 날짜가 `confirmed.date`와 같은가.

4. 사용자가 선택한 숙소·식당을 임의로 다른 후보로 바꾸지 않았는가.

이 검증을 통해 장기 대화의 성공 사례는 유지하면서도 날짜 드리프트와 선택 장소 누락을 방지할 수 있다.

​

## 10. 핵심 기술 원리

1. **상태와 문장의 분리:​** 답변 문장은 상태를 설명할 뿐 상태 자체가 아니다. Confirmed, Proposed, Rejected, Superseded를 구분한다.

2. **제약 우선 필터링:​** 필수 조건을 위반한 후보는 점수가 높아도 순위에 넣지 않는다.

3. **근거 수준 관리:​** Verified / Strongly Supported / Inferred / Unknown을 구분하고 표현 강도를 맞춘다.

4. **최소 수정 원칙:​** 날짜가 바뀌면 가격·운영시간만 재검증하고, 무관한 취향과 동행자 조건은 보존한다.

5. **Fail-closed:​** 안전·법·예산·예약 손실에 영향을 주는 미확인 조건이 있으면 추천하지 않는다.

## 11. 운영 및 심층 인터뷰 대비

### 11.1 무료 모델만 사용해야 한다면&#x20;

### (모델이 수용가능한 한계가 존재 세션, 글자수제한을 고려해야한다)

* 한 번에 긴 계획을 생성하지 않고 `정보 추출 → 누락 확인 → 후보 필터 → 검증 → 출력`으로 단계를 분리한다.

* JSON 형태의 TripState를 매 턴 짧게 유지해 문맥 손실을 줄인다.

* 가격·운영시간은 모델 기억에 맡기지 않고 공식 출처 확인 체크리스트를 강제한다.

* 후보 수를 3개 이하로 제한하고, 최종 감사 프롬프트를 별도 실행한다.

### 11.2 정책·수치가 자주 바뀐다면

* 가격·운항·입국 규정·영업시간에 `verified_at`, `source`, `stale_after`를 저장한다.

* 공식 기관·사업자 출처를 우선하고, 예약·출발 직전에 재검증한다.

* 최신 근거가 없으면 수치 대신 확인 절차를 출력하고 추천을 보류한다.

### 11.3 10턴 이상에서 문맥이 끊긴다면

* 자연어 대화 전체가 아니라 구조화된 TripState를 요약 메모리로 사용한다.

* 사용자 수정은 `replace`, 선호 변화는 `rerank`, 예약 취소는 `remove commitment`로 처리한다.

* 매 응답 전 날짜·인원·예산·확정 선택 네 항목을 자동 대조한다.

## 13. 결론

TripCare의 최종 설계는 “많이 추천하는 챗봇”이 아니라 **검증된 조건에서만 추천하고, 변경된 상태를 정확히 유지하는 의사결정 시스템**이다. 실제 대화에서 확인된 조기 예산 확정과 날짜 드리프트를 핵심 실패 사례로 삼았으며, Production v1.4는 추천 문턱, 근거 등급, 상태 전이, 출력 범위 제어로 이를 보완한다.

> **TripCare 정도의 복잡한 시스템은 채팅으로 "감"에 의존해 수정하는 단계는 어느 시점에서 끝나야 합니다. 그 이후에는 API와 평가 하네스를 이용해 동일한 테스트셋을 반복 실행하면서 객관적인 수치로 품질을 관리하는 것이 훨씬 적합합니다.​**

이 방식을 쓰면 "이번 답변이 좋아 보인다"가 아니라, **"100개의 동일한 테스트에서 92개를 통과했다"​**처럼 재현 가능한 품질 평가가 가능해집니다. 이는 실제 LLM 기반 시스템을 개발·운영할 때 널리 사용하는 접근 방식입니다.
