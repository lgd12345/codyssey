# GenAI 기초 1: LLM 기반 업무 자동화

> 동일한 업무를 3종 이상의 LLM으로 비교하고, 업무용 AI의 시스템 프롬프트를 설계한 뒤, 10턴 이상의 대화와 환각 검증을 수행하는 과제입니다.

---

## 과제 한눈에 보기

이 과제는 크게 세 단계로 진행됩니다.

```text
1. 동일한 업무를 3종 이상의 LLM에 수행시켜 비교
2. 선택한 업무에 맞는 페르소나·시스템 프롬프트 설계
3. 10턴 이상 대화하고 환각·문맥 유지 여부 검증
```

### 최종 제출물

| 산출물 | 수량 | 핵심 내용 |
|---|---:|---|
| LLM 모델 비교·선정 보고서 | 문서 1개 | 3종 이상 모델 비교, 점수표, 최종 선정 근거 |
| 시스템 설계 문서 | 문서 1개 | 문제 정의, 페르소나, 시스템 프롬프트, Few-shot, 검증, 개선 이력 |
| 실행 로그 | 대화 로그 1개 | 10턴 이상 대화 전문, 문제 지점, 수정 결과 |

### 반드시 충족해야 하는 핵심 조건

- 서로 다른 LLM 3종 이상 비교
- 동일한 업무 과업과 동일한 입력 사용
- 평가 축 4개 이상
- 모델별 1~5점과 점수 근거
- 업무 과업 1개 정의
- 입력 템플릿 1개 이상
- Few-shot 예시 3개 이상
- 모호한 입력에 되묻는 Few-shot 예시 1개 포함
- 일반 프롬프트 v1과 단계적 접근 프롬프트 v2 비교
- 사실 기반 환각 검증 질문 5개 이상
- 10턴 이상 실제 대화
- 조건 변경 또는 뒤늦은 추가 정보 상황 1개 이상 포함

# 1. 미션 소개

같은 AI를 사용하더라도 질문과 지시를 어떻게 설계하느냐에 따라 결과물의 수준이 크게 달라질 수 있습니다.

이번 미션의 출발점은 다음 차이를 직접 확인하는 것입니다.

```text
그냥 물어보기 ≠ 업무에 맞게 제대로 지시하기
```

이번 미션에서는 대규모 언어 모델(LLM)의 작동 원리를 이해하고, 프롬프트 엔지니어링을 통해 원하는 텍스트 결과물을 정교하게 제어하는 방법을 익힙니다.

먼저 3종 이상의 LLM에 동일한 업무 과업을 수행시켜 결과를 비교합니다.

이때 단순한 느낌이 아니라 다음과 같은 평가 축과 근거를 사용해 최적의 모델을 선정합니다.

- 정확성
- 한국어 자연스러움
- 긴 문맥 유지
- 형식 준수
- 속도와 안정성
- 비용
- 도구 연동 적합성

그다음 특정 페르소나를 가진 업무용 AI 챗봇을 설계합니다.

설계 과정에는 다음 요소가 포함됩니다.

- 시스템 프롬프트
- 유저 프롬프트
- Few-shot 예시
- 단계적 추론 유도
- 출력 형식 규칙
- 안전장치
- 사실 검증 규칙

마지막으로 10턴 이상의 대화를 수행하면서 다음 문제를 확인하고 개선합니다.

- 환각
- 문맥 끊김
- 조건 변경 미반영
- 출력 형식 불일치

최종 목표는 AI를 단순 검색 대용이 아니라 업무 생산성을 높이는 도구로 활용할 수 있는 프롬프트 설계·검증·개선 역량을 갖추는 것입니다.

최종 선정 결론에는 해당 모델이 업무 과업에 가장 적합한 이유를 **3줄 이상**으로 설명해야 합니다.

다만 재현 가능성을 위해 원본 대화 로그 전문도 별도 파일로 남겨야 합니다.

- 생성 결과의 사실 오류를 검증하는 방법

# 4. 기능 요구 사항

다음 요구사항을 모두 충족해야 합니다.

## 4.1 모델 비교 및 선정

서로 다른 LLM 3종 이상을 선정하고, 동일한 업무 과업과 동일한 입력을 사용해 결과를 비교합니다.

### 모델 예시

- GPT-4o
- Claude 3.5 Sonnet
- Gemini 1.5 Pro
- 동급 또는 유사 목적의 최신 모델

### 비교 보고서 필수 항목

| 항목 | 요구사항 |
|---|---|
| 비교 대상 모델명 | 사용한 모델의 정확한 이름 |
| 사용 환경 | 웹, 앱, API 중 무엇인지 기록 |
| 평가 축 | 최소 4개 이상 |
| 점수 | 모델별 각 평가 축에 1~5점 |
| 점수 근거 | 왜 해당 점수를 줬는지 설명 |
| 최종 선정 결론 | 업무에 가장 적합한 모델과 이유 |
| 선정 근거 분량 | 3줄 이상 |

## 4.2 업무 자동화 과업 정의

아래 예시 중 하나를 선택하거나 본인 업무에 준하는 과업을 정의합니다.

### 과업 예시

- 메일 초안 작성
  - 요청
  - 상황
  - 톤 지정
- 회의록 요약
  - 결정사항
  - Action Items 추출
- 보고서 개요 생성
  - 목차
  - 핵심 메시지
  - 리스크
- 요구사항 정리
  - 사용자 스토리
  - 수용 기준

### 선택한 과업에 반드시 명시할 내용

- 타겟 사용자
  - 누가 사용하는가?
- 입력 데이터 형태
  - 어떤 정보를 받는가?
- 출력 규격
  - 어떤 형식으로 결과를 내야 하는가?
- 입력 템플릿 1개 이상
  - 재사용 가능한 형태로 작성

### 입력 템플릿 예시

```text
[목적]
[대상]
[핵심 포인트]
[톤]
[금지어]
[필수 포함 항목]
```

## 4.3 페르소나와 시스템 프롬프트 설계

### 페르소나 필수 요소

- 이름
- 역할 또는 직무
- 전문 분야
- 말투
- 금지 사항
- 우선순위
  - 예: 정확성 vs 친절함

### 시스템 프롬프트 필수 요소

- 역할과 페르소나
- 업무 목표
- 출력 형식 규칙
  - 제목
  - 불릿
  - 표현 톤 등
- 안전장치
  - 모르면 모른다고 말하기
  - 필요한 경우 확인 질문하기
- 사실·정책·수치 처리 규칙
  - 근거 제시
  - 확인 필요 표시

## 4.4 Few-shot 예시

동일한 업무 과업에 대해 좋은 입력과 좋은 출력의 예시를 최소 3개 제공합니다.

### 필수 조건

- Few-shot 예시 총 3개 이상
- 3개 중 1개는 모호한 입력
- 모호한 입력에서는 AI가 무엇을 되물어야 하는지 제시

즉, 모든 입력에 즉시 답하도록 만들기보다 정보가 부족한 경우 먼저 확인 질문을 하도록 설계해야 합니다.

## 4.5 단계적 추론 유도와 전·후 비교

같은 업무 입력에 대해 두 버전을 비교합니다.

### v1: 일반 지시

간단한 프롬프트를 사용합니다.

```text
아래 회의 내용을 요약해줘.
```

### v2: 단계적 접근 유도

예를 들어 다음 순서로 처리하도록 지시합니다.

```text
1. 요구사항 정리
2. 누락된 정보 확인
3. 필요한 확인 질문
4. 초안 작성
5. 지정된 형식으로 최종 출력
```

### 최종 출력 규칙

불필요하게 긴 추론 과정이 최종 답변에 그대로 노출되지 않도록 해야 합니다.

예시:

```text
내부적으로 단계적으로 검토하되,
최종 답변에는 핵심 근거 3개만 bullet로 제시
```

## 4.6 환각 검증

이 과제에서 환각은 다음과 같이 정의합니다.

> 사실, 수치, 정책, 계산처럼 정답이나 검증 가능한 근거가 필요한 질문에서 근거 없이 틀린 정보를 확신해서 답하는 것

창의적 글쓰기 자체는 환각으로 보지 않습니다.

다만 창작물은 허구임을 명시하거나 설정한 세계관 규칙을 지켜야 합니다.

### 검증 질문 수

- 사실 기반 검증 질문 5개 이상

### 질문별 기록 항목

- 기대 정답 또는 정답 판정 기준
- 허용 오차
  - 필요한 경우
- 참고 근거
  - 출처 링크는 권장되지만 필수는 아님

### Pass 기준

다음 A 또는 B 중 하나라도 충족하면 Pass입니다.

#### A. 정답과 근거 제시

- 정답을 맞힘
- 근거를 간단히 제시하거나 확인 가능한 방식을 설명

#### B. 불확실성 인정과 확인 절차 제안

- 모르면 모른다고 명시
- 확인이 필요하다고 표시
- 어디서 무엇을 확인해야 하는지 제안

### Fail 기준

다음 중 하나라도 해당하면 Fail입니다.

- 틀린 사실을 단정적으로 말함
- 근거나 불확실성 표시가 없음
- 질문의 전제가 불명확한데도 확인 질문을 하지 않음
- 임의로 사실을 만들어 답함

## 4.7 10턴 이상 대화와 문맥 유지 검증

선택한 업무 과업 시나리오로 10턴 이상 대화를 수행하고 전문을 남깁니다.

### 반드시 포함할 상황

다음 중 1개 이상을 포함합니다.

- 대화 중간에 조건 변경
  - 톤 변경
  - 대상 변경
  - 정책 변경
- 추가 정보가 뒤늦게 제공됨
  - 첨부 내용
  - 제약 조건

### 문맥 유지 Pass 기준

다음 조건을 모두 만족해야 합니다.

- 이전에 확정된 요구사항을 10턴 내내 일관되게 유지
  - 톤
  - 대상
  - 금지어 등
- 조건 변경이 들어오면 변경된 부분만 반영
- 변경되지 않은 나머지 조건은 유지

# 7. 제약 사항

## 7.1 모델과 환경 기록

재현성을 위해 다음 정보를 제출물에 반드시 기록합니다.

| 기록 항목 | 내용 |
|---|---|
| 모델명 | 사용한 정확한 모델명 |
| 요금제 | 무료 또는 유료 |
| 사용 채널 | 웹, 앱, API |
| 사용 날짜 | YYYY-MM-DD |
| 주요 설정 | 가능한 범위에서 temperature, top_p, max_tokens 등 |

무료 버전을 사용한 경우 무료 버전이라 제한된 점을 1줄로 명시합니다.

## 7.2 안전과 윤리

- 폭력적 콘텐츠 생성을 시도하지 않습니다.
- 선정적 콘텐츠 생성을 시도하지 않습니다.
- 개인정보를 프롬프트나 로그에 직접 포함하지 않습니다.

### 포함 금지 개인정보 예시

- 실명
- 전화번호
- 주소
- 계정정보

## 7.3 사실·정책·수치 처리

사실, 정책, 수치가 포함된 답변은 반드시 다음 규칙을 따라야 합니다.

- 근거 제시
- 확인 필요 표시

## 7.4 제출물 편집

대화 로그를 그대로 덤프하지 않습니다.

가독성을 위해 다음 요소를 추가해 정리합니다.

- 섹션
- 번호
- 요약

다만 재현 가능성을 위해 원본 로그 전문은 별도 파일로라도 남겨야 합니다.

# 8. 결과 예시

아래 예시는 정답이 아니라 참고용입니다. 실제 문구와 구성은 달라도 됩니다.

## 8.1 모델 비교 보고서 예시

### 비교 축

1. 정확성
   - 사실
   - 계산
2. 한국어 자연스러움
3. 긴 문맥 유지
   - 10턴
4. 형식 준수
   - 템플릿 출력
5. 속도와 안정성
6. 비용
   - 요금제
   - 토큰
7. 도구 연동 적합성

### 결론 예시

> “회의록 요약” 과업은 긴 문맥 유지와 형식 준수가 중요하므로 해당 축 점수가 높은 모델을 채택.

## 8.2 업무 과업 입력 템플릿 예시

```text
[업무 과업] 회의록 요약

[원문] 회의 메모 또는 녹취 요약 텍스트

[원하는 결과] 결정사항 / Action Items / 리스크 / 후속 일정

[톤] 간결, 사내 공유용

[금지] 추측성 표현 금지, 인물 실명 대신 역할명 사용

[확인 질문 규칙] 정보가 부족하면 최대 3개까지 질문 후 요약 시작
```

## 8.3 페르소나와 시스템 프롬프트 예시

### 페르소나

프로젝트 매니저 출신 업무 자동화 코치

### 원칙

1. 사실·수치·정책은 확인 가능해야 함
2. 정보가 부족하면 질문
3. 최종 출력은 템플릿 준수

### Few-shot 예시

**입력**

```text
회의 메모가 너무 길어.
결정사항과 할 일만 뽑아줘.
대신 확실한 내용만.
```

**출력**

```text
- 결정사항: ...
- Action Items: 담당 / 기한 / 작업 ...
- 확인 필요: ... (근거 부족 항목)
```

## 8.4 단계적 추론 유도 전·후 예시

### v1

```text
아래 회의 내용을 요약해줘.
```

### v2

```text
1. 먼저 목표 출력 항목인 결정사항, 할 일, 리스크를 선언
2. 정보가 부족하면 최대 3개 확인 질문
3. 마지막에 지정된 템플릿으로 출력
4. 최종 답변에는 핵심 근거 3개만 짧게 추가
```

## 8.5 환각 검증 기록 예시

**질문**

```text
(업무 규정) 출장비 정산 규정의 예외 조건이 뭐야?
```

### Pass 예시

> 규정 문서가 없으면 확답 불가. 사내 위키 또는 규정 PDF의 ‘예외’ 섹션을 확인해야 함. 확인 후 요약 제공 가능.

### Fail 예시

> 예외는 무조건 ... 입니다.

실제 근거 없이 단정하므로 Fail입니다.

## 8.6 10턴 대화 로그 예시

```text
1. 사용자: 회의록 원문 제공
2. AI: 누락 정보를 확인하기 위한 질문 2개
3. 사용자: 추가 정보 제공
4. AI: 템플릿 요약 출력
...
9. 사용자: 톤을 더 단호하게, 책임자를 역할명으로 바꿔줘
10. AI: 변경된 조건을 반영하고 기존 결정사항은 유지
```
