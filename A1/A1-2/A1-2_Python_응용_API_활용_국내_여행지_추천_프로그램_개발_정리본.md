# Python 응용: API 활용 국내 여행지 추천 프로그램 개발

> LLM API와 지도/장소 검색 API를 연결하여, 사용자가 입력한 여행 날짜를 바탕으로 추천 지역·날씨·행사·맛집 정보를 조합하고 최종 Markdown 여행 리포트를 생성하는 Python API 연동 과제입니다.

​

Python에서 API를 호출한다는 게 처음엔 막막하게 느껴집니다. 그런데 한 번 연결되는 순간, 가능성이 달라집니다.

LLM API가 추천을 하고, 지도 API가 위치를 찾고, 최종 리포트가 생성되는 흐름 — 이걸 손으로 조합합니다.

단일 API 호출이 아니라 여러 API를 엮어 인사이트를 만드는 과정, 그게 이번 미션입니다.

현대 서비스의 대부분은 API를 통해 데이터를 주고받습니다. AI 기능, 지도 데이터 등 다양한 서비스를 API로 손쉽게 연동할 수 있습니다.

이 미션에서는 LLM API와 지도 API를 조합하여 국내 여행 추천 프로그램을 개발합니다. 사용자가 여행 날짜를 입력하면, LLM이 해당 시기에 여행하기 좋은 지역을 추천하고, 지도 API로 맛집 정보를 검색한 뒤, 최종 여행 리포트를 생성합니다.

단순히 하나의 API를 호출하는 것을 넘어, 여러 API의 데이터를 조합하고 AI로 인사이트를 도출하는 프로그램을 만들어봅니다.

## 과제 한눈에 보기

이 과제는 크게 다섯 단계로 진행됩니다.

```text
1. CLI에서 여행 날짜 입력
2. LLM API로 추천 지역·날씨·행사 정보 생성
3. 지도/장소 API로 추천 지역의 맛집 검색
4. 두 API 결과를 조합해 최종 여행 리포트 생성
5. 원본 JSON + Markdown 리포트 저장 및 오류 처리
```

### 최종 제출물

| 산출물                |          수량 | 핵심 내용                                     |
| ------------------ | ----------: | ----------------------------------------- |
| CLI 기반 Python 프로그램 |          1개 | `-date "YYYY-MM-DD"` 입력, API 연동, 진행 로그 출력 |
| 원본 데이터 JSON        |       1개 이상 | 1차 추천 결과 + 맛집 검색 결과 + 오류 요약               |
| 최종 여행 리포트          | Markdown 1개 | 추천 지역, 이유, 날씨, 행사, 맛집, 1일 일정              |
| README.md          |          1개 | 프로그램 개요, 실행 방법, API 키 설정, 결과 확인, 보안 주의사항  |

### 반드시 충족해야 하는 핵심 조건

* Python 3.10 이상 사용

* `argparse`를 활용한 CLI 실행

* 필수 입력 옵션: `-date "YYYY-MM-DD"`

* 잘못된 날짜 형식 검증

* LLM API 1개 사용

  * OpenAI 계열 또는 Google Gemini 계열

* 지도/장소 검색 API 1개 사용

  * Kakao Local 또는 Naver Local Search

* LLM 1차 결과를 JSON으로 파싱

* 1차 추천 JSON의 `recommended_city`를 다음 API 입력으로 사용

* 맛집 검색 결과를 최종 리포트 생성에 연결

* LLM JSON 파싱 실패 시 재시도 최대 1회

* 지도 API 실패 또는 검색 결과 0건이어도 리포트 생성 계속

* API 키를 코드에 직접 작성하지 않음

* `.env` 또는 환경변수로 키 관리

* `results/` 폴더에 원본 JSON과 Markdown 파일 저장

* 오류 내용을 `errors` 배열로 관리

### 구현 원칙

1. **과제 명세와 평가기준의 필수사항은 생략하거나 대체하지 않는다.​**

2. 필수사항 안에서 **가장 단순하고 명확하게 구현한다.​**

3. 코드가 복잡해지지 않게한다.

4. 다른 환경에서도 오류가 생기지 않게 단순하게 한다.

5. 특정 문법이나 패턴을 억지로 많이 사용하지 않는다.

6. API 연결, 오류 처리, 보안, 결과 저장이 **실제로 동작하는지 확인한다.​**

### ⚠️ 제출 전에 반드시 다시 확인할 항목

아래 항목은 기능이 대체로 동작해도 하나씩 빠지기 쉬운 부분입니다. 구현 중간과 제출 직전에 반드시 다시 확인합니다.

* `argparse`를 사용하고 **-date "YYYY-MM-DD"​를 필수로 지원**한다.

* 문서 예시에는 `--date`도 등장하므로, 가능하면 `-date`와 `--date`를 둘 다 받을 수 있게 구성한다.

* 날짜는 문자열만 받는 것이 아니라 실제 `YYYY-MM-DD` 형식인지 검증하고, 잘못되면 사용법을 출력한 뒤 종료한다.

* 1차 LLM 응답은 자유 텍스트가 아니라 **JSON으로 파싱 가능한 형태**로 요청한다.

* 1차 JSON은 `recommended_city`, `weather`, `events`, `reason`의 **키 존재 여부와 타입을 모두 검증**한다.

* `recommended_city`를 실제 지도/장소 API 검색 입력으로 연결한다.

* 지도/장소 검색 결과가 0건이어도 프로그램을 중단하지 않고 최종 리포트를 계속 만든다.

* 지도/장소 API의 인증·네트워크·쿼터 오류가 발생해도 맛집을 `데이터 없음`으로 처리하고 다음 단계로 진행한다.

* LLM JSON 파싱 실패 시 재시도는 **최대 1회**만 한다.

* 오류는 `errors` 리스트에 누적하고 원본 JSON에 포함한다.

* 최종 Markdown에는 **추천 지역, 추천 이유, 날씨, 행사/축제, 맛집, 1일 일정**을 포함한다.

* 결과 예시에는 1일 일정 앞에 `(선택)` 표기가 있지만 기능 요구사항에서는 포함 항목으로 제시되어 있으므로, **구현하는 쪽이 안전하다.​**

* API 키는 코드, README, JSON, Markdown, 로그, **스크린샷 어디에도 노출하지 않는다.​**

* `.env`를 사용하면 `.gitignore`에 반드시 추가한다.

* `results/`에 원본 JSON과 최종 Markdown이 실제로 생성되는지 확인한다.

* 보너스를 구현하지 않더라도 평가에서 **캐싱으로 API 비용을 줄이는 방법**을 설명할 수 있게 준비한다.

* 추천 도시가 너무 넓거나 애매할 때의 **검색어 정규화 전략**도 설명할 수 있게 준비한다.

> **명세 해석 주의**
>
> `-date`와 `--date` 예시가 함께 등장합니다. 과제 요구사항상 `-date`는 반드시 지원하고, 혼동을 줄이려면 `--date`도 별칭으로 함께 지원하는 방법이 안전합니다.
>
> 또한 결과 파일 저장 기준은 문구상 “실행 날짜 기준”이라고 되어 있지만 예시 파일명은 사용자가 입력한 여행 날짜를 사용합니다. 제출 직전 기준을 다시 확인하고, 구현 시에는 **입력 여행 날짜를 파일명에 포함**하는 방식이 예시와 가장 잘 맞습니다.

# 1. 미션 소개

Python에서 API를 호출하는 것은 처음에는 어렵게 느껴질 수 있습니다.

하지만 API가 한 번 연결되기 시작하면 프로그램에서 활용할 수 있는 기능의 범위가 크게 넓어집니다.

이번 미션에서는 다음과 같은 흐름을 직접 구현합니다.

```text
사용자 날짜 입력
    ↓
LLM API
    ↓
추천 여행 지역 + 날씨 + 행사 정보
    ↓
지도/장소 검색 API
    ↓
추천 지역의 맛집 정보
    ↓
LLM API
    ↓
최종 여행 리포트 생성
```

LLM API가 여행 지역을 추천하고, 지도 API가 해당 지역의 장소 정보를 찾고, 마지막으로 두 결과를 다시 조합하여 하나의 여행 리포트를 생성합니다.

즉, 단순히 하나의 API를 호출하는 것이 아니라 **여러 API의 출력과 입력을 연결하여 하나의 프로그램 흐름을 만드는 것**이 핵심입니다.

현대 서비스의 대부분은 API를 통해 서로 데이터를 주고받습니다.

AI 기능, 지도 데이터, 검색 서비스 등 여러 기능을 API로 연결할 수 있기 때문에 이번 미션에서는 다음 경험을 얻는 것이 중요합니다.

* REST API 요청/응답 이해

* GET/POST 방식 이해

* JSON 데이터 처리

* 한 API의 출력을 다른 API의 입력으로 활용

* API 오류 처리

* API 키 보안 관리

* 최종 결과 파일 저장

최종적으로는 여러 외부 서비스를 연결하고, 각각의 결과를 구조화하여 하나의 새로운 결과를 만들어내는 프로그램을 구현하게 됩니다.

## REST API

* REST API의 요청과 응답 구조

* HTTP `GET`과 `POST`의 차이

* API 요청 시 Header, Parameter, Body 등이 어떤 역할을 하는지

### 평가에서 설명할 GET / POST 기준

| 구분          | GET                         | POST                        |
| ----------- | --------------------------- | --------------------------- |
| 주 용도        | 서버의 데이터를 조회                 | 서버에 데이터를 보내 처리·생성 요청        |
| 입력 위치       | 주로 Query Parameter + Header | 주로 JSON Body + Header       |
| 이번 과제의 대표 예 | 지도/장소 검색                    | LLM 추천·리포트 생성 요청            |
| 확인할 점       | 검색어, 좌표, 개수, 인증 Header      | JSON Body 구조, 모델, 인증 Header |

실제 HTTP 메서드는 **선택한 API 제공자의 공식 문서에 맞춰 구현**해야 합니다. 평가에서는 “GET/POST를 썼다”에서 끝나는 것이 아니라 **어디에 무엇을 사용했고, 그 API의 역할상 왜 그 방식을 사용했는지** 설명할 수 있어야 합니다.

## 4.1 CLI 인터페이스

### 필수 옵션


## 4.2 API 제공자 선택 규칙

두 종류의 API를 각각 하나씩 선택하여 사용합니다.

### LLM API — 택 1

* OpenAI 계열 API

* Google Gemini 계열 API

> **이번 프로젝트 선택**
>
> * LLM: Codyssey Naito — OpenAI 호환 방식
>
> * 지도/장소 검색: Kakao Local API
>
> 개발 전 Naito의 Base URL, model 이름, 인증 방식, 요청/응답 형식을 확인합니다.

### 지도/장소 검색 API — 택 1

* Kakao Local

  * 키워드 기반 장소 검색

  * 카테고리 기반 장소 검색

* Naver Local Search

  * 지역/장소 검색

### 다른 API 제공자를 사용하는 경우

다른 제공자를 사용해도 되지만 다음 공통 조건을 만족해야 합니다.

1. 국내 장소 검색이 가능해야 함

2. 응답을 JSON으로 받을 수 있어야 함

3. 최소한 다음 값 또는 이에 준하는 값을 확보할 수 있어야 함

```text
place_name
address
lat
lng
url
```

좌표는 API에 따라 다음과 같이 표현될 수 있습니다.

```text
lat / lng
```

또는

```text
x / y
```

`url`은 제공 가능한 경우 포함합니다.

### 구현 시작 전에 먼저 선택할 항목

```text
LLM API
[ ] OpenAI 계열
[ ] Google Gemini 계열

지도/장소 검색 API
[ ] Kakao Local
[ ] Naver Local Search

API 키 관리
[ ] .env
[ ] 운영체제 환경변수

보너스
[ ] 복수 지역 추천
[ ] 결과 캐싱
[ ] 보너스 미구현
```

선택하지 않은 제공자의 코드를 모두 구현할 필요는 없습니다. 다만 평가에서는 **지도/장소 API 제공자를 바꾸더라도 변경 범위를 최소화하려면 어떻게 설계할 것인지** 설명할 수 있어야 합니다.

### 지도 API 교체를 고려한 공통 데이터 구조

Kakao와 Naver는 응답 필드 이름이 다를 수 있으므로, 외부 API의 원본 응답을 프로그램 전체에 퍼뜨리기보다 `search_restaurants()` 내부에서 공통 구조로 변환하는 방식을 권장합니다.

```python
restaurant = {
    "name": "...",
    "address": "...",
    "category": "...",
    "url": "...",
    "lat": None,
    "lng": None,
}
```

```text
Kakao 응답 ─┐
            ├─> search_restaurants() ─> 공통 restaurants 구조 ─> 저장/리포트
Naver 응답 ─┘
```

이 구조를 사용하면 제공자를 바꿀 때 주로 **인증, 요청 파라미터, 응답 변환 부분만 수정**하면 되고 JSON 저장과 리포트 생성 코드는 그대로 유지하기 쉽습니다.

## 4.3 LLM API 연동 — 날씨/행사 정보

첫 번째 LLM 호출에서는 사용자가 입력한 날짜를 기반으로 여행 지역을 추천합니다.

### 입력

```text
date
```

예:

```text
20XX-03-15
```

### 핵심 요구사항

LLM에게 일반 문장으로 답하도록 요청하는 것이 아니라 **반드시 JSON으로 파싱 가능한 텍스트를 출력하도록 프롬프트를 설계**해야 합니다.

### 1차 JSON 최소 스키마

```json
{
  "recommended_city": "제주",
  "weather": "3월 중순 평균적으로 비교적 온화한 날씨",
  "events": [
    "행사 후보 1",
    "행사 후보 2"
  ],
  "reason": "추천 근거"
}
```

### 필수 키와 타입

| 키                  | 타입              | 설명                |
| ------------------ | --------------- | ----------------- |
| `recommended_city` | string          | 추천 여행 지역          |
| `weather`          | string          | 해당 시기의 일반적인 날씨 요약 |
| `events`           | array of string | 행사/축제 후보 1\~3개    |
| `reason`           | string          | 추천 근거 2\~4문장      |

> **구현 확인**
>
> * LLM 응답을 실제 JSON으로 파싱합니다.
>
> * `recommended_city`, `weather`, `events`, `reason`의 존재 여부와 타입을 확인합니다.
>
> * `recommended_city`는 다음 Kakao API 검색에 실제로 사용합니다.

### 중요 평가 포인트

이번 미션에서는 실제 날씨나 행사 정보의 정확도 자체를 평가하는 것이 핵심이 아닙니다.

중요한 것은 다음 두 가지입니다.

```text
1. LLM 결과를 구조화된 JSON으로 받는 것
2. 해당 JSON을 다음 API 단계의 입력으로 연결하는 것
```

### ⚠️ 1차 LLM 프롬프트 설계에서 반드시 명시할 내용

이번 과제에서는 프롬프트 설계가 다음 단계의 성공 여부에 직접 연결됩니다.“여행지를 추천해줘”처럼 자유 텍스트만 요청하면 안 되고, **JSON만 출력하도록 조건을 명확하게 적어야 합니다.​**

권장 조건:

```text
- JSON 객체만 출력
- Markdown 코드블록 사용 금지
- recommended_city: string
- weather: string
- events: string 배열 1~3개
- reason: string 2~4문장
- JSON 앞뒤에 설명 문장 출력 금지
```

예시 프롬프트:

```text
입력 날짜: {date}

해당 시기에 국내에서 여행하기 좋은 지역 1곳을 추천하세요.

반드시 아래 구조의 유효한 JSON 객체만 출력하세요.
Markdown 코드블록이나 추가 설명은 출력하지 마세요.

{
  "recommended_city": "string",
  "weather": "string",
  "events": ["string"],
  "reason": "string"
}
```

### 왜 자유 텍스트가 아니라 JSON인가?

자유 텍스트는 사람이 읽기에는 편하지만 다음 프로그램 단계에서 특정 값을 안정적으로 꺼내기 어렵습니다.

JSON으로 받으면 다음처럼 명확하게 다음 API 입력으로 연결할 수 있습니다.

```python
city = recommendation["recommended_city"]
```

즉, JSON은 LLM의 답변을 **다음 프로그램 단계가 사용할 구조화 데이터**로 바꾸는 역할을 합니다.

### JSON 파싱 성공만으로 끝내면 안 되는 이유

`json.loads()`가 성공해도 다음처럼 잘못된 데이터가 올 수 있습니다.

```json
{
  "recommended_city": 123,
  "weather": [],
  "events": "축제",
  "reason": null
}
```

따라서 필수 키뿐 아니라 타입도 검증합니다.

```python
def validate_recommendation(data):
    required = {
        "recommended_city": str,
        "weather": str,
        "events": list,
        "reason": str,
    }

    for key, expected_type in required.items():
        if key not in data:
            return False
        if not isinstance(data[key], expected_type):
            return False

    if not all(isinstance(item, str) for item in data["events"]):
        return False

    return True
```

검증 흐름:

```text
LLM 응답
    ↓
json.loads()
    ↓
필수 키 4개 확인
    ↓
필드 타입 확인
    ↓
events 내부 원소가 string인지 확인
    ↓
정상 데이터만 다음 API에 전달
```

## 4.4 지도/장소 검색 API 연동 — 맛집 검색

1차 추천 JSON에서 다음 값을 가져옵니다.

```text
recommended_city
```

이 값을 지도/장소 검색 API에 전달하여 해당 지역의 맛집을 검색합니다.

### 검색 개수

맛집 N곳을 검색합니다.

권장:

```text
5곳
```

### 맛집 데이터 최소 필드

각 맛집에는 가능한 범위에서 다음 정보를 저장합니다.

| 필드                       | 타입     | 설명         |
| ------------------------ | ------ | ---------- |
| `name`                   | string | 맛집 이름      |
| `address`                | string | 주소         |
| `category`               | string | 음식점 카테고리   |
| `url`                    | string | 상세 페이지 URL |
| `x`, `y` 또는 `lat`, `lng` | number | 위치 좌표      |

### Kakao Local 인증 예시

인증 헤더에 API 키를 넣어 요청합니다.

`401` 또는 `403` 오류가 발생하면 다음 항목을 확인합니다.

* API 키

* API 권한

* 도메인 설정

* 인증 헤더 형식

### Naver Local Search 인증 예시

클라이언트 ID와 Secret을 요청 Header에 포함합니다.

`401` 또는 `403` 오류가 발생하면 다음 항목을 확인합니다.

* Client ID 값

* Client Secret 값

* Header 이름 오타

* API 사용 권한

### 검색 결과가 0건인 경우

검색 결과가 없어도 프로그램이 중단되면 안 됩니다.

다음과 같이 처리합니다.

```text
맛집 검색 결과: 0건
        ↓
restaurants = []
        ↓
다음 단계로 계속 진행
        ↓
최종 리포트에서 "데이터 없음" 표시
```

> **실패 처리**
>
> * 정상 검색: 권장 5곳을 공통 맛집 구조로 정리
>
> * 검색 0건: 빈 목록으로 처리하고 계속 진행
>
> * 인증/네트워크/쿼터 오류: `errors`에 기록하고 리포트 생성 계속

### 0건이어도 리포트를 계속 만드는 이유

맛집 검색 한 단계가 실패했다고 추천 지역, 날씨, 행사 정보까지 모두 버릴 필요는 없습니다.

따라서 다음처럼 성공한 데이터는 유지하고 실패한 부분만 명확하게 표시합니다.

```markdown
## 맛집 추천

- 데이터 없음 (장소 검색 결과 0건)
```

내부 데이터는 다음처럼 유지할 수 있습니다.

```python
restaurants = []

errors.append({
    "step": "place_search",
    "type": "EMPTY_RESULT",
    "message": "0 results"
})
```

이 정책은 외부 API 일부가 실패해도 가능한 결과를 계속 제공하는 **부분 실패 허용 방식**으로 설명할 수 있습니다.

## 4.5 LLM API 연동 — 최종 리포트 생성

두 번째 LLM 호출에서는 앞 단계의 모든 결과를 조합합니다.

### 입력

1. 1차 추천 JSON

2. 맛집 검색 목록

   * 0건일 수도 있음

### 출력

Markdown 형식의 최종 여행 리포트를 생성합니다.

### 필수 포함 항목

* 추천 지역

* 추천 이유 요약

* 날씨 요약

* 행사/축제 목록

* 맛집 리스트

* 1일 일정 제안

### 맛집 검색 결과가 없는 경우

다음과 같이 표시합니다.

```markdown
## 맛집 추천

- 데이터 없음
```

### 1일 일정

구체적인 시간표까지 만들 필요는 없으며 다음 정도의 수준이면 됩니다.

```text
오전
오후
저녁
```

> **주의:​** 결과 예시에는 `1일 일정`이 `(선택)`처럼 보이지만, 기능 요구 사항에는 리포트 포함 항목으로 적혀 있으므로 오전/오후/저녁 수준으로 구현합니다.

## 4.6 에러 처리

API 호출과 JSON 파싱 과정은 `try-except`를 사용하여 예외를 처리합니다.

> **필수 정책**
>
> * API 키 없음 → 즉시 종료
>
> * LLM JSON 파싱 실패 → 최대 1회 재시도
>
> * Kakao API 실패 → 맛집 `데이터 없음`, 전체 리포트는 계속 생성
>
> * 오류 발생 → `errors` 목록에 누적

### 오류 목록 관리

프로그램 내부에서 오류를 리스트로 관리합니다.

예시:

```python
errors = []
```

오류가 발생하면 필요한 정보를 저장합니다.

예시:

```python
errors.append({
    "step": "place_search",
    "type": "AUTH_ERROR",
    "message": "HTTP 401"
})
```

오류가 없다면 빈 리스트여도 됩니다.

```json
"errors": []
```

### errors를 최종 리포트에 반영하는 방법

`errors`는 원본 JSON에만 저장하고 끝내지 않고, 필요하면 최종 Markdown에도 요약합니다.

오류가 있는 경우:

```markdown
## 오류 요약

- place_search / AUTH_ERROR / HTTP 401
- recommendation / JSON_PARSE_ERROR / retry failed
```

오류가 없는 경우:

```markdown
## 오류 요약

- 없음
```

이렇게 하면 프로그램이 일부 실패했더라도 **어느 단계에서 어떤 문제가 있었는지 최종 결과만 보고도 확인**할 수 있습니다.

### API 키 미설정

API 키가 없다면 즉시 프로그램을 종료합니다.

그리고 사용자에게 설정 방법을 안내합니다.

```text
API 키가 설정되지 않았습니다.
.env 또는 환경변수에 API 키를 설정해주세요.
```

### 401 / 403 인증 오류 디버깅 순서

인증 오류가 발생하면 무작정 코드를 수정하기보다 아래 순서로 확인합니다.

```text
1. 키 / Client ID / Secret이 실제로 설정되어 있는지 확인
2. 환경변수 이름과 os.getenv() 이름이 정확히 같은지 확인
3. Authorization/Header 이름과 값 형식을 확인
4. 해당 API 서비스가 활성화되어 있고 사용 권한이 있는지 확인
5. 도메인/IP/플랫폼 제한 설정이 필요한지 확인
6. 요청 URL과 엔드포인트가 맞는지 확인
7. status code와 응답 body를 확인
```

실제 API 키 값 자체는 디버깅 로그에 출력하지 않습니다.

### 지도/장소 API 실패

다음 이유로 지도 API 호출이 실패할 수 있습니다.

* 네트워크 오류

* 인증 오류

* 쿼터 초과

* 기타 API 오류

이 경우에도 전체 프로그램을 중단하지 않습니다.

```text
지도 API 실패
    ↓
맛집 데이터 = []
    ↓
errors에 오류 기록
    ↓
최종 리포트 생성 계속
```

최종 리포트의 맛집 부분은 다음과 같이 처리합니다.

```text
데이터 없음
```

### LLM JSON 파싱 실패

LLM이 올바른 JSON을 반환하지 않은 경우 재시도를 수행할 수 있습니다.

재시도 방식은 다음 중 하나입니다.

1. 동일 요청 재시도 1회

2. 프롬프트를 수정해 “필수 키만 다시 JSON으로 출력” 요청

재시도 횟수는 **최대 1회**입니다.

무한 재시도는 허용하지 않습니다.

### 재시도 프롬프트 예시

첫 응답이 불완전 JSON이거나 JSON 밖에 설명 문장이 섞였다면 두 번째 요청에서는 출력 형식을 더 강하게 제한합니다.

```text
이전 응답은 JSON 파싱에 실패했습니다.

아래 4개 키만 포함한 유효한 JSON 객체를 다시 출력하세요.

recommended_city: string
weather: string
events: array of string
reason: string

JSON 앞뒤에 설명을 쓰지 마세요.
Markdown 코드블록을 사용하지 마세요.
```

권장 흐름:

```text
첫 LLM 응답
    ↓
필요하면 코드블록 표시 정리
    ↓
json.loads()
    ↓
스키마 검증
    ↓
실패
    ↓
재요청 1회
    ↓
다시 json.loads() + 스키마 검증
    ↓
그래도 실패하면 errors에 기록
```

평가에서는 단순히 “재시도했다”가 아니라 **첫 실패 후 두 번째 프롬프트를 어떻게 더 제한했는지** 설명할 수 있어야 합니다.

## 4.7 API 키 관리 — 보안

API 키를 Python 코드 안에 직접 작성하지 않습니다.

잘못된 예:

```python
OPENAI_API_KEY = "실제_API_KEY"
```

다음 방식 중 하나를 사용합니다.

### 환경변수

```python
import os

api_key = os.getenv("OPENAI_API_KEY")
```

### `.env`

`python-dotenv` 등을 사용할 수 있습니다.

예:

```text
OPENAI_API_KEY=...
KAKAO_API_KEY=...
```

`.env` 파일은 GitHub에 업로드되지 않도록 `.gitignore`에 추가하는 것이 필요합니다.

다음 자료에도 실제 API 키가 노출되면 안 됩니다.

* Python 코드

* README

* 실행 로그

* JSON 결과 파일

* Markdown 리포트

* 스크린샷

프로그램 실행 시 `results/` 폴더를 생성합니다.

예시:

```text

    ↓
지역별 결과 저장
    ↓
최종 리포트 구성
```

## 보너스 2. 결과 캐싱 — 간단 버전

같은 날짜로 프로그램을 다시 실행했을 때 기존 JSON 결과가 있으면 API를 다시 호출하지 않는 기능입니다.

예:

```text
-date 20XX-03-15 입력
        ↓
results/20XX-03-15_raw.json 존재 여부 확인
        ↓
있음 ─→ 기존 JSON 사용
없음 ─→ API 호출
```

기존 결과를 이용해 리포트만 다시 생성하거나 기존 리포트를 그대로 사용할 수 있습니다.

### 배움 포인트

* API 호출 비용 절감

* 프로그램 실행 속도 개선

* 캐싱의 기본 원리 이해

### 평가에서 “코드의 어디를 바꿀 것인가?”에 대한 답변

캐싱을 추가한다면 **첫 LLM API를 호출하기 전에** 같은 날짜의 원본 JSON이 있는지 확인합니다.

```python
raw_path = f"results/{date}_raw.json"

if os.path.exists(raw_path):
    # 기존 JSON 불러오기
    # LLM/장소 API 호출 생략
else:
    # LLM 추천 호출
    # 장소 검색 호출
    # raw JSON 저장
```

구조:

```text
날짜 입력
    ↓
같은 날짜 raw JSON 존재?
 ┌───────┴───────┐
있음              없음
↓                  ↓
기존 JSON 사용    API 호출
↓                  ↓
└────── 리포트 생성 ──────┘
```

`main()`에서 API 호출 직전에 확인하거나 `load_cached_result(date)` 같은 함수로 분리할 수 있습니다.

# 7. 제약 사항

## 7.1 보안 — 필수

API 키를 다음 위치에 직접 작성하지 않습니다.

* Python 코드

* README

* 결과 JSON

* 결과 Markdown

* 제출 스크린샷

API 키는 `.env` 또는 환경변수를 사용합니다.

### 환경변수 또는 `.env`가 필요한 이유

#### 1. 키 노출 방지

협업하거나 GitHub에 코드를 올릴 때 실수로 API 키가 공개되는 것을 방지할 수 있습니다.

#### 2. 키 교체 용이

API 키가 변경되어도 프로그램 코드를 수정할 필요가 없습니다.

#### 3. 과금 및 쿼터 사고 예방

외부에 키가 공개되어 다른 사람이 사용하면 예상하지 못한 API 비용이나 쿼터 사용이 발생할 수 있습니다.

​

## 7.2 환경변수 설정 예시

### macOS / Linux

현재 터미널 세션에서 다음과 같이 설정할 수 있습니다.

```bash
export OPENAI_API_KEY="YOUR_KEY"
```

### Windows PowerShell

```powershell

```

위 값은 설정 방식의 예시입니다.

실제 API 키는 제출물에 절대 포함하지 않습니다.

​

## 7.3 운영 안정성

다음 원칙을 권장합니다.

### API 키 미설정

```text
즉시 종료
+
키 설정 방법 안내
```

### 지도/장소 API 실패

```text

+

```

### LLM JSON 파싱 실패

재시도는 최대 **1회**만 허용합니다.

```text
첫 파싱 실패
    ↓
재요청 1회
    ↓
성공 또는 오류 처리
```

무한 재시도는 금지합니다.

## 7.4 추천 도시가 너무 넓거나 애매할 때의 검색어 정규화

LLM이 `경기도`, `강원도`, `경상남도`처럼 너무 넓은 지역을 반환하면 맛집 검색 품질이 떨어질 수 있습니다.

가능한 대응:

1. LLM 프롬프트에서 **시/군/구 수준으로 추천**하도록 조건을 추가한다.

2. 검색어를 `"{recommended_city} 맛집"`처럼 보정한다.

3. 광역 단위 결과를 감지하면 더 구체적인 도시명을 다시 정한다.

4. 자주 나오는 표현은 내부 정규화 함수로 통일한다.

```python
def normalize_city(city):
    aliases = {
        "제주도": "제주",
        "부산광역시": "부산",
        "대구광역시": "대구",
    }
    return aliases.get(city.strip(), city.strip())
```

핵심은 **지도 API를 호출하기 직전에 입력을 정리**하여 제공자와 관계없이 검색 품질을 안정화하는 것입니다.
